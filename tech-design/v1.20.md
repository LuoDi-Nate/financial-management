### 按账户聚合的入口(要收口的清单)

| 路径 | 位置 | 今天怎么按账户分组 |
|---|---|---|
| 归因 | `AttributionEngine.groupBy` ← `AttributionService.accountLabels` | `dimKey == null` 走账户特例 |
| 透视 | `PivotEngine` | `byAccount.putIfAbsent(position.accountId(), …)` 去重后按账户度量 |
| 镜头 / 分布 | `LensQueryService` | 按 `Position.accountId` |

**四条,靠人记必漏** —— 所以选型一的判据是「结构上不可能漏」,不是「记得改全」。

### 静默失败预检

**这个设计里,哪些失败会不报错、不降级、结果照常渲染?**

| 可能的静默失败 | 为什么静默 | 怎么让它响 |
|---|---|---|
| **单属被破坏**(同一账户进两个组) | 合计变大,但归因把差额**吸进「未归因」** —— 数字看着平了 | **DB 唯一索引**(不能只靠应用层校验)+ 恒等式断言进 e2e |
| **折叠漏掉某条聚合路径** | 那条路径照旧按账户展开,页面正常渲染,只是「没折叠」 | grep 护栏扫「所有聚合入口是否都过了同一个解析器」+ 零组态逐字比对 |
| **定格用错时点**(按当前成员关系算历史) | 历史图会变,但每个数字自身都「算对了」 | e2e:建组后已关账月份的数字必须一字不变 |
| **组内流转用毛额求和** | 抵消失效,组的现金流虚高;但恒等式仍然闭合(毛额也是自洽的) | 护栏钉死「组内成员求的是净额」+ 单测造一笔组内划转 |

## 一、需求分析

### 1. 背景 & 目标

见 [`prd/v1.20.md`](../prd/v1.20.md) §0,不重复。

**技术上为什么现在做**:分组 B 会大量改动聚合路径,而 `pivot` 与 `period_summary`
两条无共用求和逻辑的路径**已经差 0.01**(潜伏问题,跟数据分布走)。
这一版是**顺手把聚合收口到一处**的合适时机 —— 再拖,收口成本只会更高。

### 2. 需求理解(验收口径)

| FR | 工程判据 |
|---|---|
| FR-450/451 | 该账户本期 `period_snapshot` 存在(即已校准)**且** 本次改动会使 `end_balance` 变化 → 返回的行片段含提示;两个条件缺一则不含 |
| FR-452 | 行片段渲染 `period_snapshot.submitted_at`(有=已校准,无=未校准) |
| FR-453 | 该账户本期**无** `period_snapshot` → 提示改用「不进本期净资产变化」话术 |
| FR-461 | `account_group_member.account_id` 上有 **UNIQUE** 索引 |
| FR-464/465 | 四条聚合路径的账户维值均来自同一个解析器;`expand=<groupId>` 时该组回落到账户维值 |
| FR-466 | 零组态下,四条路径的输出与 tag `v1.19.16` **逐字一致** |
| FR-467 | 组的现金流 = Σ(成员 `transferIn − transferOut`),即**净额求和** |
| FR-468 | 归因/趋势读的是 `period_account_group` 定格行,不是当前 `account_group_member` |

## 二、关键选型

### 选型一 · 折叠层挂在哪

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 四条聚合路径**各自**处理分组 | 改动局部 | **四份真相**,必然漏一条;而且漏了不报错 | 不选 |
| B | 在事实层把 `AccountPeriodFact.accountId` **改写成 groupId** | 下游零改动 | **丢失账户粒度**,FR-465 的下钻做不了;而且污染了事实层 —— 事实应该是事实 | 不选 |
| **C** | **把「账户」从特例维度变成和其它维度一样的标签维度**,四条路径共用一个解析器 | 结构上不可能漏;下钻只是换一次标签;零组态逐字一致是**必然**而非需要保证 | 要动 `groupBy` 的账户特例分支 | **选它** |

**选定理由**:今天账户是特例 —— `groupBy(result, "acct".equals(dim) ? null : dim)`,
传 `null` 表示「按账户」。而 `assetClass / owner / platform / currency / type` 都走
`accountLabels(familyId)` 返回的 `accountId → {dim → label}` 映射。

**把 `acct` 也放进这张映射表**,标签取值:

```
已分组   → 组名(该期定格的组名)
未分组   → 账户名
```

于是:

- **零组态时**,每个账户的 `acct` 标签就是自己的账户名 → 输出与今天逐字一致,**这是结构上必然的**,
  不需要额外保证,也不需要开关(PRD FR-466)
- **下钻**(FR-465)= 给解析器传一个 `expandGroupId`,该组成员的标签回落成账户名,其余不变
- **新增一条聚合路径**时,它必须问解析器要标签 —— 漏不掉

**为什么不是「新增一个 group 维度」**:那样用户在 `acct` 维度下仍然看到满屏噪声,
还得记住「要换个维度看」。折叠必须发生在账户维度**自己身上**(PRD 已裁定)。

### 选型二 · 组内流转怎么剔除

**前置检查推翻了我的第一直觉。** 我原以为要在事实层带上对手方账户,
但 `AccountPeriodFact` 只有每账户每期的 `transferIn/Out` 汇总。

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 扩展 `FactMapper` 查询与 `AccountPeriodFact`,带上对手方 | 语义显式 | 要改事实层结构与 SQL,影响面大;而且**没必要**(见 B) | 不选 |
| B2 | 单独查 `transfer` 表,识别两端同组的行再扣掉 | 不动事实层 | 多一条查询路径,**又是一处可能漏的地方** | 不选 |
| **B** | **靠「按组求净额」自动抵消** | **不需要任何对手方识别**;结构上必然;零新增查询 | 只对**净额**成立,毛额会失效 → 要护栏 | **选它** |

**为什么 B 成立** —— 这是本版最值得记的一条:

```
A → B,两端都在组内:
    A.transferOut += X        B.transferIn += X
    组内求净额 = Σ(in − out) = X − X = 0        ✅ 自动抵消

A → C,C 在组外:
    A.transferOut += X        (C 不在组内,不参与求和)
    组内求净额 = 0 − X = −X                      ✅ 正确计为流出
```

**组内流转的剔除是「按组求净额」的副产品,不需要专门实现。**
代价是这条性质**很容易被无意破坏** —— 有人把某处改成毛额求和,抵消就失效了,
而且**结果仍然自洽**(毛额也闭合),不会报错。所以它必须有护栏 + 单测(见 §六)。

**已知残差 · 跨币种组内划转**

`transfer` 有 `amount`(转出币种)与 `to_amount`(转入币种)。事实层把两端各自按
**该期汇率快照**换算到 view 币种。若快照汇率与这笔划转的实际成交汇率不同:

```
残差 = (fx_快照 − fx_实际) × 金额
```

**这不是本版引入的** —— 今天全家层面的划转抵消已经有同一个问题。
**待实测**(§零)要量一下它的实际量级:

- 0.01 级 → 归入既有的 `KNOWN-PIVOT-VS-KPI-ROUNDING`,一并处理
- 百分级 → 必须给方案。**倾向如实显示 + 建组时提示**「跨币种组的组内划转会留汇率残差」,
  **不倾向**用划转自带的隐含汇率强行配平 —— 那等于在事实层编一个汇率

### 选型三 · 组成员关系怎么定格

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 不定格,历史一律按当前成员关系折叠 | 零成本 | **改一次组成员,12 期趋势图全变** —— 用户会当成算错了 | 不选 |
| **B** | **复刻 `period_account_attr`**:关账时写入 `period_account_group`,重开时删除 | 与 v1.12 **同一条规则**,不新造机制;「重开后再关账 = 重新定格」是结构上必然 | 多一张表 | **选它** |
| C | 成员关系带生效区间(有效期版本) | 理论上最精确 | 与本项目的账期语义不一致(这里的时间单位是**账期**,不是时刻);复杂度不成比例 | 不选 |

**选定理由**:v1.12 已经为「关账 = 分类属性定格」建立了完整机制,
包括 `reopen()` 删定格行、`close()` 重新定格,而且这两处**已经在同一个事务里**。
分组定格挂进去是**加一行调用**,不是造一套机制。

顺带:v1.19.16 刚在 `reopen()` 里加了「清 AI 复盘缓存」,同一个位置。
**`reopen()` 正在变成「该期所有派生物的失效点」** —— 这是个好现象,写进 AGENTS.md。

### 选型四 · 分组 A 的提示放在改动前还是改动后

**这是 preview 与 FR 文字之间的一处张力,必须现在解决。**

preview 第 1 屏画的是**改动前**(「你正在删掉…删掉之后它会变成…」+ 两个按钮);
而 PRD FR-450 边界写的是「提示是**信息**不是**拦截**。按下去就该过,不设二次确认弹窗」。

| 方案 | 用户体验 | 优 | 劣 |
|---|---|---|---|
| A · 改动**前** | 点删除 → 行内展开提示 → 点「知道了」才真删 | 能**避免**推翻 | 每次都多一次点击;而且提示里的「会变成 X」是**预测值** |
| **B · 改动后** | 点删除 → 直接生效 → 行内出现结果条:「已删。这个账户余额 09-02 校准过,刚从 X 变成 Y」+「去重新校准」 | **零额外点击**,严格符合「不拦截」;数字是**实际值**不是预测 | 他得再动一次去修 |

**推荐 B。** 理由是回到提交者的原话:

> 「就会导致已经校准的余额失效!……我觉得至少有个**强烈的提醒**」

**他的痛点是「不知情」,不是「不该改」。** 而且他改收入,往往正是因为收入记错了 ——
余额跟着修正**本来就是对的**。事后如实告知已经解决了他的问题,且不给所有人加一次点击。

**代价是真实的**:如果他确实不想让余额变,B 让他多做一次操作。但那是少数情形。

> **需要你点头的一处**:选 B 的话,preview 第 1 屏的措辞要从「你正在删掉…」改成
> 「已删掉…」,按钮从「知道了 / 去重新校准」变成「去重新校准 / 知道了」。
> **要不要改,你定** —— 也可以坚持 A,那 FR-450 的边界表述要跟着松一句。

## 三、系统概要设计

### 1. 整体设计思路

```
              ┌────────────────────────────────┐
  建组/改组 ──▶│  account_group                 │  用户维护(可选)
              │  account_group_member  UNIQUE  │  ← 单属靠 DB 索引
              └───────────────┬────────────────┘
                              │ close() 时定格
                              ▼
              ┌────────────────────────────────┐
              │  period_account_group          │  该期快照(reopen 时删)
              └───────────────┬────────────────┘
                              │
                              ▼
              ┌────────────────────────────────┐
   四条聚合 ──▶│  AccountGroupingResolver       │ ← **唯一入口**
   路径全部    │  labelsFor(familyId, periodId, │
   问它要标签  │            expandGroupId)      │
              │  → Map<accountId, 维值>        │
              └────────────────────────────────┘
```

**一句话**:把「账户」从聚合里的特例,变成一个**有标签的普通维度**,标签由唯一的解析器给。

### 2. 领域模型设计

| 概念 | 定义 | 边界 |
|---|---|---|
| **账户组** | 可选的叠加聚合层,含 1..N 个账户 | **不是账户的属性**(账户表不加列)· **不是记账实体**(不能对着它填余额/记收支/导截图) |
| **组成员关系** | 账户 → 组的归属 | **一个账户最多属一个组**(DB 唯一索引)· 未分组的账户不产生任何行 |
| **该期分组** | 关账时定格的成员关系快照 | 重开即删,再关账重新定格 —— 与分类属性定格同一条规则 |
| **组内流转** | 两端账户在同一维值内的划转 | 不计入该组现金流;**由净额求和自动实现**,不单独建模 |

定稿后同步进 `AGENTS.md` 领域概念节。

### 3. 代码架构设计

| 新增/改动 | 职责 |
|---|---|
| `AccountGroup` / `AccountGroupMember`(domain) | 组与成员关系 |
| `AccountGroupMapper` / `PeriodAccountGroupMapper`(repo) | CRUD + 定格 / 删定格 |
| **`AccountGroupingResolver`(service)** | **唯一入口**。`labelsFor(familyId, periodId, expandGroupId)` → `Map<Long accountId, String 维值>`。未分组账户返回账户名 |
| `AccountGroupService` | 建组 / 改组 / 删组 · 推荐分组(`LIQUID` / `isLiability()`)· 跨类型提示 |
| `AttributionService.accountLabels` | 加一个 `"acct"` 维度的标签,取自解析器 |
| `AttributionEngine.groupBy` | 去掉账户特例分支(`dimKey == null`),统一走标签 |
| `PivotEngine` / `LensQueryService` | `byAccount` 的键从 `accountId` 换成解析器给的维值 |
| `PeriodService.close/reopen` | 各加一行:定格 / 删定格 |
| `EntryService.recordIncome/deleteIncome/...` | 返回改动前后余额 + 该期校准时间,供行片段渲染(分组 A) |

**不产生第二条求和路径** —— 解析器只负责**给标签**,求和仍在各自引擎里做。
这是刻意的:如果解析器也负责求和,就又多了一条口径。

### 4. 运行架构

**无新进程、无新定时任务。** 解析器是请求内的一次查询,按 `(familyId, periodId)` 在请求作用域内缓存即可。

### 5. 物理架构

**不适用** —— 单机部署形态不变。

### 6. 数据架构设计

| 表 | 变化 | 旧行怎么办 |
|---|---|---|
| `account_group` | **新增**:`id, family_id, name, created_at` | — |
| `account_group_member` | **新增**:`group_id, account_id` · **`UNIQUE(account_id)`** | — |
| `period_account_group` | **新增**:`period_id, account_id, group_id, group_name, sealed_at` · `PK(period_id, account_id)` | — |
| 既有表 | **一律不改** | 零影响 |

**迁移三问**:

1. **只加不改**?✅ 三张新表,既有表一列不动
2. **能回滚**?✅ 回滚 = 删三张表。jar 回滚后表还在但没人读,**不影响旧代码**
3. **中途失败**?三个 `CREATE TABLE` 各自独立,失败重跑幂等(`IF NOT EXISTS`)

**`group_name` 冗余进定格表是刻意的**:组被改名或删除后,历史仍然显示当时的名字 ——
和 `period_account_attr` 冗余 `product_category_name` 同一个理由。

## 五、稳定性与质量保障

### 1. 兼容性设计

| 情形 | 行为 |
|---|---|
| 老数据 + 新代码 | 零组态 → 解析器返回账户名 → **与 v1.19.16 逐字一致** |
| 新数据 + 老代码(回滚窗口内) | 三张新表没人读;`period_account_group` 里的定格行被忽略 → 退回按账户展示。**不报错、不丢数据** |
| 没建组的用户 | **一个像素都不变** |

### 2. 性能评估

**基本不适用** —— 单家庭量级(账户数 < 50,期数 < 200)。

需要留意的只有一处:解析器**不能在循环里被调用**。
它按 `(familyId, periodId)` 一次查询、请求内缓存;
如果出现「每个账户调一次解析器」就是 N+1 —— 落进护栏。

### 3. 安全性设计

**不适用** —— 无凭据、无对外面、无 LLM、无文件上传。

一处留意:分组 A 的结果条含账户名与金额,只在已登录填报页渲染,
与该页既有内容同级 —— 不进日志、不进审计表。

## 六、护栏设计

| 护栏 ID | 守的设计意图 | 判据怎么写 |
|---|---|---|
| `v1200-SINGLE-GROUP-MEMBERSHIP` | 单属靠 **DB** 保证,不靠应用层 | 迁移脚本里必须有 `UNIQUE` 索引在 `account_group_member.account_id` 上;应用层校验**不算数** |
| `v1200-ONE-RESOLVER` | 四条聚合路径**共用**解析器,没有旁路 | 扫 `AttributionEngine` / `PivotEngine` / `LensQueryService` / 收益路径:出现按 `accountId` 直接分组的写法就红。**守「有没有旁路」,不守具体数量** |
| `v1200-NET-NOT-GROSS` | 组内流转靠**净额求和**自动抵消 | 组级现金流的实现里必须是 `in − out` 的求和,不许出现分别累计毛额再相减以外的写法;配单测:造一笔组内划转,组的净流入必须为 0 |
| `v1200-FROZEN-NOT-LIVE` | 历史读**定格**行,不读当前成员关系 | 归因/趋势路径不许直接引用 `AccountGroupMapper`;只能走 `PeriodAccountGroupMapper` |
| `v1200-REOPEN-CLEARS-GROUP` | 重开账期要删该期定格(与清分类属性、清 AI 复盘缓存同一处) | `PeriodService.reopen()` 里三个 `deleteByPeriod` 都在 |
| `v1200-ZERO-GROUP-IDENTICAL` | 零组态与 tag `v1.19.16` 逐字一致 | e2e 快照比对 |
| `v1200-NO-N-PLUS-1` | 解析器不在循环里调 | 扫调用点不在 `for` / `stream().map` 内 |

**三条纪律照 `_TEMPLATE.md`**:守意图不守写法 · 能机器校验的别只写文档 ·
本版没有依赖 LLM 的护栏(不适用)。

**特别提醒**:`v1200-ONE-RESOLVER` 最容易写成「数四条路径」——
那就是第五次「护栏绑在偶然事实上」。判据必须是**「有没有旁路」**。

## 七、上线与回滚方案

### 1. 可观测

- `/health` + 发版后健康验证
- 建组 / 改组 / 删组走 `audit_log`(`SYSTEM` 类型,target=`account_group`)
- 定格与删定格**落日志**,含该期账户数 —— 定格数量对不上时能查

### 2. 预案评估

| 出问题 | 怎么办 | 可逆? |
|---|---|---|
| 折叠显示不对 | **用户自己删组**即可回到未分组(FR-463) | ✅ 完全可逆 |
| 口径算错 | 回滚 jar;三张新表留着不影响旧代码 | ✅ |
| 迁移失败 | 三个建表各自独立,重跑幂等 | ✅ |

**无不可逆动作** —— 不发外部请求、不在第三方侧创建删除、不重写历史数据。

### 3. 上线方案

1. 迁移:三张新表(`IF NOT EXISTS`),**不停机**
2. beta 验证清单(**必须走用户实际点击路径**,不能只测端点):
   - 零组态:四条路径与 tag `v1.19.16` 逐字比对
   - 建「随时可取」组 → 归因折叠成一行 → 点开下钻回到 4 个账户
   - 组内互转一笔 → 该组净流入为 0;转给组外 → 不为 0
   - 关账定格 → 改组成员 → **已关账月份数字一字不变** → 重开再关账 → 按新分组重算
   - 删组 → 数据零变化、页面回到未分组
   - 分组 A:该提示的提示、不该提示的不提示(正反两面)
3. 灰度替代物:**没建组 = 零影响**,用户自己决定何时开始用
