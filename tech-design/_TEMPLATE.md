# TDD 模板

> 骨架取自 [`tech-design/v1.19.md`](v1.19.md)(它照的是维护者给的大厂 TDD 模板),
> 再按本项目实际裁过。**配套**:需求见 [`prd/_TEMPLATE.md`](../prd/_TEMPLATE.md)。
>
> **两份分工不许混**:PRD 写用户视角的「要什么」,TDD 写「怎么做 + **为什么这么做**」。
> 「为什么这么做」是 TDD 存在的理由 —— 一份只有代码清单的 TDD 等于没写。

---

## 怎么用:按版本大小分档

| 版本类型 | 写哪几节 |
|---|---|
| **补丁 / 小版本**(`x.y.Z`) | 通常**不新建文件**,写成上一个大版本 TDD 的**附录**(见文末「附录约定」)。至少要有:根因 · 选型 · 修法 · 护栏 |
| **大版本**(`x.Y.0`) | 全套;确实不适用的节写「不适用 · 理由」而不是删掉 |

「不适用」也要留一行 —— 删掉的话,下一版就不知道这一节被想过没有。

## 零、前置检查

**这一节是本项目最该较真的地方。** v1.19 连错四次(握手版本、请求体形状、字段名与动词、
会话三步)—— 每一次的共同点都是:**没有对着真实的第三方跑一次就开始写代码**。

### 依赖方接口能力核对(已查证)

| 能力 | 文档怎么说 | **实测是什么** | 一致? |
|---|---|---|---|
| … | … | … | ✅ / ❌ |

**硬规矩:文档与实测不一致时,以实测为准,并且必须把不一致写在这里。**
我们已经遇到过官方文档写「加这个头就会流式」而实测根本不流式的情况 ——
如果不写下来,下一个人会再信一次文档。

### 待实测(阻塞编码)

列出**还没验证、但会决定设计**的点。这一节没清空之前不许开始写代码。

- [ ] …

### 静默失败预检

**问自己:这个设计里,哪些失败会「不报错、不降级、HTTP 200」?**

本项目最贵的 bug 全是这一类:字段名发错被上游静默忽略、缓存没有失效入口、
把「追加事件」的响应当成「答案流」来读。它们的共同表现是**读起来完全通顺**。

| 可能的静默失败 | 怎么让它响 |
|---|---|
| … | 写完回读确认 / 回执校验 / 护栏 |

## 一、需求分析

### 1. 背景 & 目标

**只写一段,别重复 PRD。** 指向 PRD 的 §0,这里补充**技术上为什么现在做**
(例如:欠债到了必须还的点、上游接口要下线了)。

把 PRD 的 FR **翻译成工程上可判定的判据**。这是 PRD 与 TDD 的接缝,最容易出歧义。

## 二、关键选型(**正文,不是附录**)

> 这一节从 v1.19 的「附录」提到了正文 —— 它是 TDD 存在的理由,不该排在补丁记录后面。

每个关键决策都要有:**2–3 个备选 · 取舍 · 选定理由 · 未选的为什么不**。

### 选型一 · <决策名>

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | … | … | … | 不选 · 理由 |
| **B** | … | … | … | **选它** |
| C | … | … | … | 不选 · 理由 |

**选定理由**:…

**两条纪律**:

1. **权重要诚实** —— 对比表里**不许出现「我写代码省不省事」那类只有我感知得到的维度**。
   用户感知不到的东西不进权重;把工作量伪装成用户价值是错的。
2. **「不选」要给理由** —— 只写选了什么,等于没做选型。
   半年后有人问「当初为什么不用 X」,答案必须在这里。

## 三、系统概要设计

### 1. 整体设计思路

一段话说清这版的技术主线。能画一张 ASCII 图最好。

### 2. 领域模型设计

**必要** —— 本项目自造概念密度高(镜头 / 持仓方向 / 开账基线 / 定格 / 流动性分层)。
新增或改动的领域概念要写清:**它是什么、和既有概念的关系、边界在哪**。

**单一定义在 `AGENTS.md`** —— 这里写的是本版的**变化**,定稿后要同步回 AGENTS.md。

### 3. 代码架构设计

新增/改动的类与职责、它们之间的依赖方向。重点回答:
**新逻辑挂在哪一层**、**会不会产生第二条求和路径**(本项目已有 pivot 与 kpi 两条路径差 0.01 的前科)。

### 4. 运行架构

**多数版本一句话就够**(单体 Spring Boot / 单实例 / systemd 或 compose)。
只有涉及新的进程、定时任务、外部长连接时才展开。

### 5. 物理架构

**默认不适用** —— 单机部署,写「不适用」。
只在**部署形态变化**时写(容器化、新增网关容器、跨机通信这类)。

### 6. 数据架构设计

| 表 | 变化 | 旧行怎么办 |
|---|---|---|
| … | 加列 / 加表 / 改约束 | … |

**迁移三问(prod 上跑着真实家庭数据)**:

1. 能不能**只加不改**?加列给默认值,比改语义安全一个数量级
2. 这个迁移**能不能回滚**?不能的话为什么可以接受
3. 迁移**中途失败**会留下什么状态?

## 四、接口协议设计

### 1. 影响评估

本版触及哪些既有接口 / 页面 / 任务。**列全** —— 靠人记必漏,所以要配 grep 护栏。

### 2. 对外接口(条件必要)

只在**真的开放对外面**时写(MCP 端点、Webhook、Open API)。要写清:

- 鉴权与失败语义(本项目约定:**未通过一律 404 且空体**,不告诉对方这里有没有东西)
- 限流
- **只读还是可写** —— 只读要靠工具层**物理不提供**写方法来保证,不靠 prompt 或约定

不涉及就写「不适用」。

### 3. 我们调用的上游接口(条件必要)

**只要有,就必须贴实测报文**(脱敏后)。文档里的示例不算数 —— 见 §零。

```
POST /xxx
请求:{ … }
实测响应:{ … }
```

## 五、稳定性与质量保障

### 1. 兼容性设计

**每版必写** —— prod 上跑着真实家庭数据。

- 老数据在新代码下怎么表现
- 新数据在老代码下怎么表现(回滚窗口内会同时存在)
- 没启用新功能的用户,看到的东西**会不会变**(答案应该是「不会」)

### 2. 性能评估

**多数版本不适用**(单家庭数据量,几百到几万行)。写「不适用 · 数据量级」。

**必须写的情形**:全表扫 / N+1 / 循环里发外部请求 / 新增定时任务 / 单次响应体明显变大。

### 3. 安全性设计(条件必要)

涉及**凭据、对外面、LLM、文件上传**时必写:

- 凭据存在哪、怎么轮换、明文出现几次
- **LLM prompt 里放什么、绝对不放什么**;脱敏在**哪一层**(要靠工具层物理不提供,不靠 prompt 约束)
- 上传文件的类型判定(靠**魔数**不靠扩展名)
- 失败信息会不会泄露内部结构

不涉及就写「不适用」。

## 六、护栏设计

> PRD 的「验收 → 护栏映射」说**要守什么**,这里写**怎么守**。

| 护栏 ID | 守的设计意图 | 判据怎么写 |
|---|---|---|
| `vXXX-YYY` | … | … |

**三条纪律(每条都是踩出来的)**:

1. **守意图,不守当下写法。** 不许绑字面量、不许绑当下的数量、不许绑当下的数据分布。
   本项目已经犯过四次:`v08-NAV-1` 绑单个路径 · `v181-FLOAT-DOCK` / `v1617-FIVE` 绑三按钮数组 ·
   `v11911` 数「出现两次」把**收口重复**误判成**退化**。
2. **能机器校验的别只写文档。** 文档会落后,护栏不会。
3. **依赖外部随机输出(LLM)的护栏,必须能区分「被守的东西坏了」和「这次外部没给结果」** ——
   否则它会用红灯消耗信任,直到没人再看它。

## 七、上线与回滚方案

### 1. 可观测(不是"监控报警")

我们没有监控体系,**对应物是这三样**:

- `/health` + 发版后的健康验证
- `audit_log` / 领域审计表(谁、什么时候、做了什么)
- 关键失败路径**必须落日志**,且日志里要有**上游原话**
  —— 「上游原话被兜底文案盖住」这个病本项目犯过三次(v1.19.4 / v1.19.11 / v1.19.14)

### 2. 预案评估

出问题时怎么办:关开关 / 回滚 jar / 回滚迁移。**哪些动作不可逆**要单独列。

### 3. 上线方案

- 迁移顺序、是否需要停机(默认不停)
- beta 验证清单(**必须包含走用户实际点击路径**,不能只测端点)
- 灰度替代物:**开关默认关**就是我们的灰度

---

## 八、成本测算(条件必要)

**只在引入按量计费的外部服务时写**(LLM、云 API、对象存储)。纯内部功能写「不适用」。

要写到能被审计的程度:计价口径 · **假设全部列出** · 单次成本 · 敏感度分析 · 月度成本。

v1.19 那次的做法值得照抄:**敏感度分析证伪了两个原本以为重要的参数** ——
如果只算一个「预计每月 X 元」,那两个错误假设就带进去了。

## 附录约定

**补丁版本(`x.y.Z`)不新建 TDD 文件,追加成本文件的附录。** 每个附录至少写:

1. **症状** —— 用户看到的是什么
2. **根因** —— 查证过程与证据(实测报文、日志、DB 状态),**不是猜测**
3. **修法与取舍** —— 为什么这么修,不那么修
4. **护栏** —— 这次落了哪条,守的是什么意图
5. **教训**(有的话)—— 同型缺陷复发时,要写明这是第几次、前几次修得太窄在哪

这个实践来自 v1.19(附录一~十三),它让「一个大版本 + 一串补丁」的完整故事留在一处,
而不是散成十几个只有 commit message 的碎片。
