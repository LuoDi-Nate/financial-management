### 静默失败预检

| 可能的静默失败 | 后果 | 怎么让它响 |
|---|---|---|
| 确认写到一半失败(还贷记了、贷款余额没写) | 付款账户扣了钱、贷款没少 | 整个确认在一个事务里;单测模拟第二步抛错,断言库里一笔都没多 |
| 同一笔点了两次(双击 / 两个人同时点) | 支出翻倍 | `(fixed_flow_id, period_id)` 唯一键 + 先占位后写;第二次直接报「这一笔这期已经确认过了」 |
| 信用卡账单被记成「还贷」支出 | 刷卡消费已经算过一次,支出翻倍(v1.19.3 说的那种) | 信用卡账单只走划转;单测 + e2e 断言确认后**没有**支出流水 |
| 方式 ② 用了错的「上月欠款」或正负号反了 | 利息变负、本金比月供大 | 纯函数单测:一整年等额本息 + 还清那期 + 月供不够利息 + 没填利率 |
| 方式 ① 与「接受」算出不同的余额 | 维护者要求的「兼容」破了 | 同一个函数;e2e 同一贷款新旧两条路逐分比对 |
| 两期同时开着,确认写进了另一期 | 补录期的钱跑到进行期 | 期由页面显式带上(L16 显式选期),服务端校验它是开着的;e2e 双开期断言 |
| 撤销时贷款余额已经被人改过 | 把人后来填的余额覆盖回去 | 只在「当前余额 == 确认时写进去的那个数」时才还原,否则不动并写明 |
| 导入去重按金额误伤 | 一笔真实消费被默认不勾,用户没看见 | 只挪进「建议跳过」(能勾回来、写明原因),不是直接丢 |
| 立即备份 mysqldump 卡死 / 写满盘 | 按钮一直转、或连点写出十个文件 | 同一时间一个(锁)+ 两次间隔 ≥ 1 分钟 + 10 分钟超时杀进程;失败写 `backup_log` FAILED 与 mysqldump 的原话 |
| 备份文件生成了但是坏的 | 以为有备份,恢复时才发现 | 与 Docker 备份同一套校验:能完整解压(GZIP 校验和)且至少有一句 `CREATE TABLE`;不过 → 删文件、记失败 |

## 一、需求分析

### 1. 背景 & 目标

见 PRD §0。技术上现在做,是因为第 2 稿把「贷款试算」并了进来:它今天只改贷款余额、起草的还款划转是死数据(`is_draft=1`),还款那笔钱永远要人另记 —— 固定收支的「还款」正好把这半截补上,并且两套东西只留一个入口。

### 2. 需求理解(验收口径)

| FR | 工程判据(可判定) |
|---|---|
| FR-1100 ~ 1105 | `fixed_flow` 一行 = 一条固定收支;`kind ∈ {INCOME, EXPENSE, REPAY, PREMIUM}`;`REPAY` 再分 `repay_kind ∈ {LOAN, CARD}`。确认 INCOME → `recordIncome`;EXPENSE → `recordExpense(affectsBalance=true)`;REPAY·LOAN → 付款账户 `recordExpense(loan_payment, 本金)`(+ `interest_paid` 利息)+ 贷款本期余额设为「上月末 + 本金」(方式 ①:`predictLoanBalance`);REPAY·CARD 与 PREMIUM → `addTransfer(付款账户 → 卡 / 保险账户)`,**没有支出流水** |

| FR-1107 | 卡片上金额旁标「算」,点开是 `FixedFlowCalc.Result.formula`;算不出来(`problem` 非空)→ 不给「确认」,只给「这期没有」,并写原因 |

| FR-1110 ~ 1114 | 填报页「第一步」卡片头下面一行 `#fixed-flows`(`<details>`,默认收起);展开后分三组:到日子的(待确认 + 贷款建议)、`还有 N 笔没到日子`、`已确认 N 笔`;「全部确认」只提交到了日子且算得出来的;改了金额 → `rememberAmount` 勾(只对固定金额出现);已确认的有「撤销」 |

| FR-1130 ~ 1133 | 入口:填报页卡片头「固定收支」按钮 + 摘要行「管理」→ `/admin/fixed-flows`;管理总览「家庭基础」组加卡片、侧栏清单加一项;记一笔收入 / 支出表单上的勾 `makeFixed`;贷款详情页「每期还款」一行 / 「设固定还款」,保险详情页保单块「设成固定交保费」 |

## 二、关键选型

### 选型一 · 固定收支存在哪、确认记录存在哪

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 给 `cash_flow` / `transfer` 加 `fixed_flow_id` 列,不要确认表 | 少一张表 | 改了两张最核心的表(PRD §6 承诺不改旧表);「这期没有」「就是它(关联到导入的那笔)」没地方记;贷款余额写了多少、撤销时还原成多少也没地方记 | 不选 |
| **B** | **两张新表**:`fixed_flow`(一条设置)+ `fixed_flow_occurrence`(某条在某期的结果:确认 / 这期没有 / 关联到导入那笔,以及这次写了哪几笔的 id、贷款余额写前写后) | 旧表一列不动;撤销按 id 精确删;唯一键 `(fixed_flow_id, period_id)` 直接挡住重复确认 | 两张表要进导出 / 清演示数据 / 家庭隔离审计 | **选它** |
| C | 一张表 + JSON 列存每期结果 | 一张表 | 唯一性、按期查询都要在代码里拼;JSON 里的 id 没法被审计脚本扫到 | 不选 |

### 选型二 · 确认写进去的东西怎么「和手动记的完全一样」(FR-1115)

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 固定收支服务自己往 `cash_flow` / `transfer` 插行、自己改余额 | 想写什么写什么 | **第二条写入路径** —— 现金行联动(v1.18.1)、补录期传导(v1.23)、负债账户不记还贷(v1.19.3)、只在消费上写分类(L13)这些规矩都得再抄一遍,漏一条就是静默算错 | 不选 |
| B | 调既有公开方法,事后按「期 + 账户 + 金额 + 时间」去找刚插的那行 | 不改既有方法 | 猜;同金额两笔就猜错,撤销删错 | 不选 |
| **C** | **调既有公开方法**,加一个可选的「写入回执」参数:里面带来源标签(`FIXED_FLOW`),方法把这次插进去的流水 / 划转 id 填回回执。不传 = 老行为(`MANUAL`) | 只有一条写入路径;来源与 id 都是写入口给出的真值 | 动了 `EntryService` 三个公开方法的签名(加重载)和两个私有插入方法 | **选它** |

回执是一个很小的可变对象(`EntryService.WriteReceipt`),只在一次调用里活着;不是 ThreadLocal —— 调用关系在签名上看得见。

### 选型三 · 还款(贷款月供)确认时贷款余额怎么写

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 在贷款上做增量:当前余额 + 本金 | 简单 | 有人这期已经按账单填过贷款余额,再加一次本金就**还了两遍** | 不选 |
| **B** | **写绝对值**:新余额 = 上月末 + 本金(方式 ① 就是 `predictLoanBalance`,与「接受」同一个数);**只在贷款本期余额还等于上月末时写**(没人动过);已经有人改过 → 只记付款账户那边的还贷 / 利息,贷款余额不动,卡片上写明 | 与「接受」逐分相同(FR-1108);不覆盖人填的数 | 「有人改过」时贷款这边要人自己核对(卡片上已写明) | **选它** |

确认记录里存 `loan_balance_before / after`;撤销时只有当前余额仍 == `after` 才还原成 `before`(选型同理:不覆盖后来人填的)。

写贷款余额用一个新的 `EntryService.setLoanBalanceBySystem`:快照 upsert(`source_tag=SYSTEM_ADJUST`)+ 补录期传导 + 标填好 + 审计 —— 与 `acceptLoanPrediction` 写快照的那几行相同,但**不起草那笔死划转**。`acceptLoanPrediction` 本身一行不改(FR-1120「结果与今天逐字相同」)。

### 选型四 · 信用卡账单记成什么

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| A · 付款账户记「还贷」支出 + 改卡的余额 | 和贷款月供同一套 | 刷卡的消费已经记过一次,再记「还贷」= 支出翻倍(v1.19.3 的教训);v1.19.3 只拦了「卡上记还贷」,这里是在现金账户上记,拦不住 | 不选 |
| **B · 一笔划转(付款账户 → 卡)** | 不算支出;两端余额由既有划转逻辑联动;收益口径里划转本来就被扣掉 | — | **选它** |

### 选型五 · 交保费按保单:缴满怎么停

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| A · 每确认一次把保单「已缴期数」+1,到总期数停 | 保单页的「已缴」跟着走 | 改了保单表(PRD 说保单只读);撤销要 −1;回滚后数对不上 | 不选 |
| **B · 建的时候按「生效月 + (总期数 − 1) 个缴费周期」算出「到哪期为止」,写进固定收支的 `end_month`** | 只读保单;到点自然停;表单上看得见、能改 | 保单后来改了总期数不会自动跟 | **选它**(金额照 PRD 跟保单走:方式 ④ 每次现读每期保费) |

### 选型六 · 「到日子」怎么算、提醒数从哪来

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| A · 定时任务每天把到期的写成「待确认」行 | 查询简单 | 新增定时任务;开关、补跑、双开期都要处理;停用 / 改日子后要清旧行 | 不选 |
| **B · 现算**:某期里「那天」= `FixedFlowSchedule.occurrenceIn`(纯函数),到没到 = 那天 ≤ 今天;待确认 = 到了 − 已有确认记录 | 没有新任务;改了设置立刻生效 | 每次打开填报页 / 仪表盘多一次小查询(一个家庭几十条,可忽略) | **选它** |

### 选型七 · 立即备份由谁来跑

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 应用写一个「请求」(表行或文件),systemd 的 path unit / Docker 备份容器轮询到了去跑 | 备份仍由备份脚本做 | 两种部署各要一套新机制(新 unit、容器轮询);v1.33「删除前先备份、成功才删」要等异步结果 | 不选 |
| B | 用 Java 自己 `SELECT` 全部表拼 SQL | 不依赖外部命令 | 自己实现一个 mysqldump(转义、类型、外键顺序)—— 出错就是「有备份但恢复不了」,而且和自动备份的格式不一样 | 不选 |
| **C** | **应用自己起 `mysqldump` 子进程**,输出流经 GZIP 写文件,写完用与 Docker 备份相同的标准校验 | 同步、成功与否当场知道(v1.33 直接复用);格式与自动备份相同;两种部署都已有 `mysqldump`(Docker 镜像里本来就装着,systemd 主机上自动备份就在用) | systemd 的 unit 要把备份目录加进可写白名单;beta 本机目录属主要改一次 | **选它** |

密码经子进程环境变量 `MYSQL_PWD` 传,不出现在命令行(`ps` 看不到);mysqldump 的 stderr 截前 400 字写进 `backup_log.error_message`(上游原话)。

## 三、系统概要设计

### 1. 整体设计思路

```
                     ┌───────────── 管理页 /admin/fixed-flows(增 / 改 / 停用)
fixed_flow ──────────┤
(一条设置)            └───────────── 记一笔时的勾「每月都有,设成固定」

填报页 ?period=X ──► FixedFlowSummaryService.build(家庭, 期, 我, 仅我?)
                        │  FixedFlowSchedule:这一期哪天该有、到了没有
                        │  FixedFlowCalc:金额(固定 / 五种自动)
                        │  + 没设固定还款的贷款 → 「建议」(来自 EntryRow.showLoanPrompt)
                        ▼
              #fixed-flows 一行摘要(展开:到日子的 / 没到的 / 已确认的)
                        │ 确认 / 这期没有 / 撤销 / 就是它
                        ▼
FixedFlowConfirmService(一个事务)──► EntryService 既有方法(带写入回执)
                        │                   recordIncome / recordExpense / addTransfer
                        │                   setLoanBalanceBySystem(新,写快照那几行)
                        ▼
fixed_flow_occurrence(这期的结果 + 写了哪几笔的 id + 贷款余额写前写后)
```

提醒数(导航 / 仪表盘 / 填报页进度)都调 `FixedFlowSummaryService.pendingCount(家庭)`,只有这一处判「待确认」。

### 2. 领域模型设计

| 概念 | 是什么 | 边界 |
|---|---|---|
| **固定收支**(`fixed_flow`) | 一条「每期都会有」的设置:种类、金额方式、账户、周期、几号、负责人、到哪期为止 | 不是流水;本身不进任何金额计算。停用不影响已记的 |
| **确认记录**(`fixed_flow_occurrence`) | 某条固定收支在某一期的结果:`CONFIRMED`(写了流水 / 划转 / 贷款余额)/ `SKIPPED`(这期没有)/ `LINKED`(就是导入的那一笔) | 一条固定收支一期最多一条;**不进任何金额计算** —— 金额只在它指向的流水 / 划转 / 快照里 |
| **待确认** | 这一期里那天 ≤ 今天、还没有确认记录、而且这期要人点的那种(总数模式下的固定支出不算) | 现算,不落库 |
| **贷款建议** | 没被任何启用中的「还款」指着的贷款,沿用今天的趋势提示判据(`loanPromptVisible`) | 不写确认记录;按钮仍是今天那两个方法 |

### 3. 代码架构设计

| 类 | 职责 |
|---|---|
| `domain/fixedflow/FixedFlow` · `FixedFlowOccurrence` | 两张表的实体;种类 / 方式 / 状态用字符串常量(同 v1.29 `instrument_kind`、v1.30 `nav_mode` 的做法,老 jar 不读这两张表,新值也不会让任何页面 500) |
| `repository/FixedFlowMapper` | 两张表的读写,全部带 `family_id` |
| `service/fixedflow/FixedFlowSchedule` | 纯函数:某期哪天、到没到、年缴月份解析 |
| `service/fixedflow/FixedFlowCalc` | 纯函数:五种自动计算 + 算式 + 算不出的原因 |
| `service/fixedflow/FixedFlowService` | 设置的增改停用 + 校验(种类 × 账户类型 × 方式);归档联动停用;「记一笔时顺手设」 |
| `service/fixedflow/FixedFlowSummaryService` | 组装填报页摘要的视图模型、待确认数;**只读** |
| `service/fixedflow/FixedFlowConfirmService` | 确认 / 全部确认 / 这期没有 / 撤销 / 就是它 —— **唯一的写入编排**,一个事务里调 `EntryService` |
| `service/backup/BackupNowService` | 立即备份:锁、间隔、跑 mysqldump、校验、写 `backup_log` |
| `web/fixedflow/FixedFlowEntryController` | 填报页上的确认类端点(表单 POST → 重定向回 `/entry?period=…#fixed-flows`) |
| `web/admin/FixedFlowAdminController` | 管理页 |

依赖方向:web → service/fixedflow → `EntryService`(写)/ mapper(读)。`FixedFlowSummaryService` **不写**,`FixedFlowConfirmService` **不自己插流水**(护栏 `v132-ONE-WRITE-PATH`)。不产生第二条求和路径:摘要里的「共 ¥X」只是待确认卡片金额之和(按本位币换算展示),不进任何指标。

### 4. 运行架构

单体不变。立即备份是请求线程里同步跑一个子进程(最长 10 分钟超时);同一时间只允许一个(进程内锁)。

### 5. 物理架构

不适用 · 部署形态不变。systemd unit 的可写白名单多一个 `/var/backup/finance`(`deploy.sh` 比对后重装)。

### 6. 数据架构设计

| 表 | 变化 | 旧行怎么办 |
|---|---|---|
| `fixed_flow` | **新表**(V71) | — |
| `fixed_flow_occurrence` | **新表**(V71),唯一键 `(fixed_flow_id, period_id)` | — |
| `cash_flow` / `transfer` | 不改结构;新写入的 `source_tag` 可能是 `FIXED_FLOW` | 老行不动 |
| `backup_log` | 不改;开始写 `MANUAL`(V5 起就允许) | — |

迁移三问:① 只加表;② 回滚 = 老 jar 不读这两张表,已确认写进去的是普通流水 / 划转 / 快照,老 jar 照常认(来源显示「来源未记录」)—— 不需要回滚 SQL;③ 迁移只有两句 `CREATE TABLE IF NOT EXISTS`,中途失败重跑即可。

## 五、稳定性与质量保障

### 1. 兼容性设计

- **没设任何固定收支的家庭**:摘要行只剩「+ 设固定收支」(有贷款建议时是建议);贷款提示从行内挪到摘要,按钮调的方法与结果不变。其它页面一个数都不变(不改口径)。
- **新数据在老 jar 下**:两张新表被忽略;已确认写进去的流水 / 划转 / 快照照常算;`source_tag='FIXED_FLOW'` 显示「来源未记录」。
- **v1.31 的备份页**:Docker 用户的文案改成按部署方式判断后,不再受「最新一条是手动」影响。

### 2. 性能评估

不适用 · 每次打开填报页 / 仪表盘多 3–4 条按家庭的小查询(固定收支几十条以内);导航徽标每页一次 —— 与现有 `countPendingByPeriod` 同量级。

### 3. 安全性设计

- 立即备份:DB 密码只经子进程环境变量;页面不提供下载(PRD §4);文件权限沿用目录属主。
- 所有新 SQL 带 `family_id`(L17);新表进 `family-isolation-audit.py`。

### 影响矩阵(写操作 × 归属判据 · L16)

| 写操作 | 写了什么 | 归属判据 |
|---|---|---|
| 确认(收入 / 支出 / 还款 / 交保费) | 流水 / 划转 / 贷款快照 + 确认记录 | **显式选期**(摘要所在的期,请求带 `periodId`) |
| 这期没有 | 确认记录 | 显式选期 |
| 就是它 | 确认记录(指向那笔导入流水) | 显式选期 |
| 撤销 | 删流水 / 划转、还原贷款快照、删确认记录 | 确认记录自己的期 |
| 贷款建议 · 接受 / 保持上月 | 与今天相同 | 显式选期(与今天相同) |
| 记一笔时顺手设 | 一条设置 + 本期一条 `LINKED` 确认记录(指向刚记的那笔) | 显式选期 |
| 立即备份 | `backup_log` + 文件 | 不涉及账期 |

各页面指标对这些写入的反应与「人在同一期手动记同一笔」逐字相同(PRD §6),不另画指标矩阵。

## 六、护栏设计

| 护栏 ID | 守的设计意图 | 判据怎么写 |
|---|---|---|
| `v132-ONE-WRITE-PATH` | 固定收支只经 `EntryService` 写流水 / 划转 / 快照,不出现第二条写入路径 | `service/fixedflow/` 下不许出现 `cashFlowMapper.insert` / `transferMapper.insert` / `snapshotMapper.upsert`;`FixedFlowConfirmService` 必须调 `entryService.` 的那几个方法 |

| `v132-CARD-IS-TRANSFER` | 信用卡账单与交保费只记划转 | 确认服务里 CARD / PREMIUM 分支只调 `addTransfer`;单测断言没有支出流水 |
| `v132-NO-SILENT-WRITE` | 系统从不自己记 | `service/fixedflow/` 里没有 `@Scheduled`;确认端点都是 POST |
| `v132-LOAN-PROMPT-MOVED` | 贷款提示从行内挪进摘要(替换 `v17-LOAN-PROMPT` 里绑 `_row.html` 的那半) | `_row.html` 不再有接受表单;摘要模板里有「接受」「保持上月」,分别指向原来那两个端点 |
| `v132-FAMILY-TABLES` | 新表进隔离审计 / 导出 / 清演示数据 | `family-isolation-audit.py` 的 DIRECT 含两张表;`CsvExportService` 写两张 CSV;`v129-DEMO-CLEAN-COMPLETE` 自然覆盖 |
| `v132-BACKUP-NOW` | 立即备份:锁 + 间隔 + 超时 + 校验 + 记原话 + 文件名落进滚动删除前缀 | `BackupNowService` 里有这几样;`finance.service` 白名单有 `/var/backup/finance`;备份页部署方式由控制器给 |
| e2e flow 48 | 页面 + 库两层(维护者 10-08 定义) | 见 §七.3 |

## 七、上线与回滚方案

### 1. 可观测

- 每次确认 / 撤销 / 这期没有写 `audit_log`(既有方法本来就写一条,本版再写一条汇总「确认固定收支 物业费 ¥480」)。
- 立即备份:`backup_log` 一行(开始即写 RUNNING,结束更新);失败原因是 mysqldump 原话;`audit_log` 记谁点的。

### 2. 预案评估

- 回滚 jar(v1.31.x):两张新表被忽略;没有不可逆动作。
- 「立即备份」本身只新增文件,由自动备份的滚动删除回收。

### 3. 上线方案

- 迁移 V71 只建表,不停机。
- **prod 部署**:`deploy.sh` 会重装 `finance.service`(白名单变了)并 `daemon-reload` + 重启。
- **beta 一次性**:`sudo chown finance:finance /var/backup/finance`(beta 目录是手建的 root 属主;prod 由 `deploy.sh` 建,属主本来就对)。
- beta 验证清单(走用户点击路径,e2e flow 48):
  1. 填报页 → 「第一步」卡片头「固定收支」→ 管理页加一条支出 → 回填报页,摘要行出现、展开、确认 → 库里多一笔 `source_tag=FIXED_FLOW` 的支出,余额扣了;撤销 → 回到原样。
  2. 记一笔支出勾「每月都有,设成固定」→ 管理页多一条、本期这条已确认(不重复出现)。
  3. 贷款:设「按上两月差值」的固定还款 → 确认 → 贷款余额 == `predictLoanBalance`,付款账户多一笔「还贷」;另一笔没设的贷款在摘要里出建议,「接受」结果与旧版一致。
  4. 信用卡账单 → 只有一笔划转、没有支出。
  5. 导航「填报 ·N」、仪表盘「未结账」条数字随之变化。
  6. 双开期:在上一期摘要确认,流水落在上一期。
  7. 管理 → 备份 → 立即备份:成功一条「手动」;连点只多一条;库里 `backup_log` 对应一行。
  8. 手机:摘要一行、展开后按钮整行。
