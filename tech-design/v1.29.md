## 零、前置检查

### 依赖方接口能力核对

| 能力 | 文档怎么说 | **实测是什么** | 一致? |
|---|---|---|---|
| 盈透 Flex `OpenPosition` 期权行的 `positionValue` 含不含乘数 | 字段参考没写清 | **含**:买入 `position=1`、`markPrice × 100 = positionValue`(2026-10-02 @Jsonya 在 #26 贴的真实报表) | — |
| 卖出期权的 `position` / `positionValue` 符号 | 没写 | **都为负**(`position=-1`、`positionValue` 负、`side=Short`) | — |
| 期权代码长度 | — | **21 个字符**(`GOOGL 270416C00360000`),现有 `ticker` 列 16 | ❌ 需加宽 |
| 期权行带不带 `multiplier` / `strike` / `expiry`(YYYYMMDD)/ `putCall` / `underlyingSymbol` | 「字段全选」时都在 | 都在 | ✅ |
| 富途 `Position.val` 对期权含不含乘数 | 文档只写「市值」 | **没有真实富途期权账户实测** | 待实测 |
| 富途卖出(空头)时 `qty` / `val` 的符号 | 文档没写 | **没有实测** | 待实测 |
| 老虎持仓接口怎么构造请求 | 官方 Java 示例:`TigerHttpRequest(MethodName.POSITIONS)` + `AccountParamBuilder.buildJson()` | SDK 2.4.2 javap 核对:`PositionsItem` 带 `@JSONField(name="items")`,`PositionDetail` 有 `positionQty / latestPrice / marketValue / multiplier / identifier / expiry / strike / right` | ✅(结构)· **没有真实老虎账号跑过** |
| 老虎持仓接口不传品种回什么 | 示例默认 `STK` | 未实测 → **按品种各查一次**,不赌默认值 | — |

**对「待实测」的处理(不阻塞,但不赌)**:富途 / 老虎的不确定点一律做成**符号跟方向走、只核对大小**:

- 富途:张数符号取 `positionSide`(Short = 负),市值取 `|val|` 再配符号;美股期权用「`|val|` ÷(张数 × 价格)≈ 100」核一遍 —— 如果富途的 `val` 其实没乘乘数,这一行会**不同步并点名**,而不是静默少 99%。
- 老虎:市值取 `|marketValue|` 配张数的符号,再用「张数 × 最新价 × 乘数」核对大小。

两家都只有单测按 SDK 数据结构核对,**发版说明里写清楚这一点**,请用这两家的人回报。

### 静默失败预检

| 可能的静默失败 | 怎么让它响 |
|---|---|
| 期权市值差 100 倍 / 符号反了,余额错得离谱但不报错 | 三家共用 `DerivativeRows.check`:张数 × 标记价 × 乘数 ≈ 市值(1 元或 1%),对不上**这一行不同步、同步结果点名**;单测放进「没乘乘数」「符号反了」两种行 |
| 期货按名义价值计入,一张合约多出几十万 | `InstrumentKind.countsInBalance()` 只对期货返回 false,解析层直接给 0;护栏 `v129-DERIV-CROSSCHECK` |
| 老虎持仓查询失败 → 0 笔 → 对账把同步来的股票全部归档 | 股票那一查失败就**抛**(与 v1.26 IBKR「失败信封不当空报表」同一条);期权 / 期货那几查失败(没开权限)只记日志 |
| 老虎资产查询失败 → 现金列表为空 → 现金行全部归档 | v0.15 起就是这样(静默)→ 改成抛出,本次不对账 |
| 老虎两个 segment 同币种 → 两条现金,后一条覆盖前一条 | 按币种相加(与测试连接那条路径一致) |
| 期权行进了基金穿透,拿「AAPL · 看涨 · …」去天天基金搜名字 | 穿透候选 SQL 加 `instrument_kind IS NULL`;护栏 `v129-DERIV-NOT-FUND` |
| 点名的行多了,同步结果超过 `last_status VARCHAR(255)` → 记成功这一步失败 → 整个事务回滚 | 落库前截到 250 字(页面 flash 仍给全文) |
| 以前为凑数手填过一条期权市值,升级后算两遍 | 第一次带进期权等、且账户里有手填行时,同步结果提醒一句(FR-955)—— 不替用户删 |

## 二、关键选型

### 选型一 · 期权等存在哪、怎么计值

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 新表 `broker_derivative_position`,估值时另加一段求和 | 语义最干净 | 估值、透视、持仓页、AI 材料都要认第二张表 —— **第二条求和路径**,本项目 pivot / kpi 差 0.01 就是这么来的;漏接一处就少算 | 不选 |
| B | 新增 `ValuationMode.BROKER` | 估值语义明确 | 所有 `switch(ValuationMode)` 与模板里 `'MANUAL'` 字面量都要补(编译器只抓 switch,抓不到模板串 —— v0.14 加 METAL 时踩过三处);**回滚 jar 时老代码读到不认识的枚举值直接炸** | 不选 |
| **C** | **沿用 MANUAL 行**:单价 = 市值 ÷ 张数(折成账户币种),张数带符号;加 `instrument_kind` 等说明列只供展示 | 估值一行不改,卖出靠负张数自然变负;回滚 jar 时老代码把它当普通 MANUAL 行(下次同步按「券商没有」归档) | MANUAL 原本暗示「手填」→ 要在页面上把它和手填区分开(徽章、估值分解、手改表单) | **选它** |

**选定理由**:用户看到的唯一结果是「余额对不对」;C 让余额只有一条计算路径,并且回滚安全。MANUAL 的「手填」暗示是展示问题,在持仓页用 `isDerivative()` 分开处理(护栏 `v129-DERIV-NOT-FUND`)。

### 选型二 · 期货计多少

| 方案 | 怎么做 | 结论 |
|---|---|---|
| A | 名义价值(张数 × 价格 × 乘数) | 不选:一张 ES 名义 30 万美元、保证金只要两万左右,账户余额会虚高十几倍 |
| B | 券商给的 `fifoPnlUnrealized` | 不选:那是自开仓以来的浮盈,而每天的盈亏已经结算进现金 —— 与现金重复计 |
| **C** | **记 0,只展示名义价值** | **选它**:期货每日结算,现金里已经反映了盈亏;与盈透净值的差只剩「上次结算到报表时点」那一点 |

### 选型三 · 债券计不计应计利息

**不计**(只用 `positionValue`)。现金的应计利息、股息应计我们本来就不记(取的是 `endingCash`);只给债券加会让口径不一致。与盈透净值的差 = 它的「应计」那一行,和现状一样。

### 选型四 · 交叉核对的容差

1 个货币单位或 1%,取大。报表里的 `markPrice` 是四舍五入过的(真实数据 `28.5419 × 100 = 2854.19`,刚好相等;但别家可能只给两位小数)。容差只为吸收舍入,**差 100 倍、符号反了都远超**。债券的标记价常按「面值的百分比」给 → 再按 /100 核一次(两种约定都认,不赌)。

### 选型五 · 富途怎么认出期权

| 方案 | 结论 |
|---|---|
| A · 另开行情连接查 `GetStaticInfo` 拿品种 | 不选:要多一条行情连接和行情权限,失败面变大;只为分个类不值 |
| **B · 按代码形状**(标的 + yyMMdd + C/P + 行权价 × 1000) | **选它**:美股 / 港股期权代码都是这个形状;股票代码(美股字母、港股 / A 股数字)长不成这样。单测覆盖港股 / A 股数字代码不被误认 |

### 选型六 · 第一次同步那一跳(维护者裁定,不是技术选型)

新账户 = 开账、已有账户 = 当月收益。**这正是现有口径自然给出的结果**:开账基线 = 账户首次出现那一期的期末(v1.28.1 起减掉首期转入);已有账户的期末变化里没有现金流,就落进「钱赚」。**代码一行不用改**,e2e flow 41 用首页账户表的「本期损益」把两种情况各验一次。

## 三、系统概要设计

### 1. 整体设计思路

```
券商(盈透 Flex XML / 富途 OpenD / 老虎 OpenAPI)
   │  各家只做一件事:把一行持仓归到 股票 / 期权等 / 没同步(带原因)/ 跳过
   ▼
BrokerDtos.Snapshot{ positions, cash, manualPositions, derivatives, rejected, skippedNonEquity }
   │  DerivativeRows.check —— 三家同一个判据
   ▼
BrokerSyncService.reconcile ── 期权等 → MANUAL 行(单价 = 市值 ÷ 张数 × 汇率,张数带符号)
   ▼
AccountValuationService(不改)── 余额 = AUTO + MANUAL(含期权等)+ CASH → period_snapshot
```

### 2. 领域模型设计

- **期权等(`InstrumentKind`)**:OPTION / WARRANT / FUTURE / BOND。是 `stock_holding` 的一种**展示分类**,不是新的估值模式。
- 与「手填市值」的关系:库里同是 MANUAL;区别是 `instrument_kind` 非空且 `sync_source` 非空 —— 由券商维护、不给手改、不进穿透。
- 与资产分类的关系:**不单列**(§13 ③),跟账户类型走;透视里负市值(卖出)按弧长取绝对值的既有规则画。
- 单一定义已写回 `AGENTS.md` §3「券商只读同步」与 L6。

### 3. 代码架构设计

| 类 | 职责 |
|---|---|
| `domain/stock/InstrumentKind` | 品种枚举 + 人话标题 / 张数文字 / 到期提示(纯函数) |
| `service/broker/DerivativeRows` | 交叉核对、没同步的那一行怎么说、到期日解析(纯函数) |
| `IbkrFlexParser.readDerivative` | OPT/FOP→期权、WAR→权证、FUT→期货、BOND→债券 |
| `FutuBrokerClient.map` | 一笔富途持仓归类(纯函数,包可见供单测) |
| `TigerBrokerClient.positions / map` | 按品种各查一次;一笔老虎持仓归类 |
| `BrokerSyncService.reconcile` | 期权等 → MANUAL 行;到期 / 平仓归档;摘要;手填重复提醒 |
| `StockHoldingController.list` + `stock/holdings.html` | 期权行写人话、估值分解单列「期权等(券商报表)」 |

**没有第二条求和路径**:估值、透视(`perHoldingLines`)、AI 材料读的都是 MANUAL 的「单价 × 张数」。

### 4. 运行架构

不变(单体 Spring Boot)。老虎同步从 1 次请求变成 1 次资产 + 6 次持仓(按品种),仍是手动 / 每日一次。

### 5. 物理架构

不适用。

### 6. 数据架构设计

| 表 | 变化 | 旧行怎么办 |
|---|---|---|
| `stock_holding` | `ticker` 16 → 48;加 `instrument_kind / underlying / put_call / strike / expiry / multiplier / quote_price / notional`(全可空) | 全是 NULL = 普通持仓,行为不变 |

迁移三问:① 只加不改(加宽是放宽约束);② 能回滚 —— 老 jar 不读新列;③ 中途失败:单条 `ALTER TABLE`,要么全成要么不动。

## 五、稳定性与质量保障

### 1. 兼容性设计

- **没有期权 / 债券 / 空头的富途、盈透账户**:对账逐字不变;页面一个像素不变(估值分解在没有期权时仍按原条件出现、仍是三格)。零差异基线对照已发布 v1.28.5。
- **老虎账户**:股票第一次进来,余额会跳(以前只有现金)—— 发版说明写明。
- **新数据在老代码下**:期权行是 MANUAL + `sync_source`,老代码估值照算;下一次同步按「券商没有」归档。
- **富途**:美股期权以前会让整次同步失败(代码 17 字符 > 16),升级后反而能同步了。

### 2. 性能评估

不适用(每个账户几十行持仓;老虎多 5 次查询、每天一次)。

### 3. 安全性设计

不涉及新凭据 / 新对外面 / LLM 改动。同步结果里点名的是合约名(标的 · 行权价 · 到期日),不含金额。

2. **根因**(证据:提交者导出的 `period_account_attr`;临时 MySQL 上照全新 Docker 安装逐条复现 —— 迁移到 V65 → 照 `docker/clean-dev-data.sh` 清演示数据 → 剩 132 条定格行;按提交者的形状建账户、建 9 / 10 月、关 9 月 → 导出与提交者逐字一样:10 月 OPEN、5 号 CASH→LOAN、10 号 LOAN→PROPERTY):V3 灌演示数据(5 号 = 招行信用卡 LOAN、10 号 = 住宅 PROPERTY,1 / 2 号期已关账)→ V54 给已关账的期 BACKFILL 定格行 → 清演示数据只 `TRUNCATE period / account`,编号重用。读的那一侧(`FactMapper.queryBase` 的 `LEFT JOIN period_account_attr`)不看期的状态,于是没关账的期也吃到了残留。
3. **修法与取舍**:
   - **读的一侧只认已关账的期**(`queryBase` join 加 `p.status = 'CLOSED'`;`findByPeriod` 两处同)。不选「只靠迁移删残留」:读侧不设防,以后任何一条写错的定格行都会再静默改写当期;而「未关账 = 按当前设置」本来就是 v1.12 的定义,读侧照定义写,正常数据零差异。
   - **V67 清残留**,判据只用「真定格不可能满足」的事实:没关账的期上的;`sealed_at` 早于期或账户的 `created_at`(都是 DATETIME(3),不存在取整误差);孤儿行。不按 `source='BACKFILL'` 一刀切 —— 升级安装的老库里 BACKFILL 行是真的。beta 上四条各 0 行。
   - **三个清演示脚本补 `TRUNCATE period_account_attr / period_account_group`**。
4. **护栏**:`v129-FROZEN-ONLY-CLOSED`(读侧条件 + V67 + flow 42)· `v129-DEMO-CLEAN-COMPLETE`(迁移里 INSERT 过的表,三个脚本都要清或在保留名单里 —— 守的是「编号重用」这一类,不是这一张表;去掉一行 TRUNCATE 实测会红)· e2e flow 42(当前期塞一条残留定格行 → 首页总负债不变、明细不列现金账户)。
5. **教训**:v1.28.4 那次「明细取最早一行的类型」是真问题,修了;但我把它当成了提交者的根因,回复里写了「升级后应该能直接看出来」—— 提交者升级后数对上了、类型却还是错的。**修一个能解释现象的 bug ≠ 找到了根因**:当时没拿到提交者的定格表就下了结论。这次是拿到数据、在全新安装上逐条复现到逐字一致才定。
