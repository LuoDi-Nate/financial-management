## 一、需求分析

### 1. 背景与目标

见PRD第0节。技术目标是在已有GoalProgress之上增加可扩展、状态独立的观察指标,共享家庭月结余,保留已发布v1.39.0的资金口径、旧退休采用流程与投资情景。

### 2. 工程判据

| FR | 工程判据 |
|---|---|
| 1450—1452 | 主结果先算,观察指标后装配;新ETA与旧neutralDate为不同字段/名称,公式只含当前缺口和月可用结余 |
| 1453—1454 | 本位币、全家庭、明确自然月边界,先逐月净结余再取中位;只用有来源的已定稿月份 |
| 1455—1456 | 保存的是偏好,不是测算快照;AUTO缺来源可保存;金额非法仅卡自己的设置表单;已达成优先于缺结余 |
| 1457 | 列表/详情/仪表盘读取同一观察指标装配器;仪表盘时间放进度轴下方元信息行,`ml-auto text-right`保证换行后仍贴右缘,去掉退休配置状态;共用片段以原`goalsHistoricalReport`标记区分报表,报表不增加今日ETA,旧AI月报不重算 |

目标小i由`GoalProgressSummary.from`只读拼装同一`GoalProgress`、退休Result及Forecast的公式、实际值和来源,不查询数据库或重算门槛/日期。R2读有效生活费与实际回报,准备金和负债各列一次;旧算法、比率及负债分别解释原口径。金额行带`data-priv`,报表传`includeForecast=false`。沿用`kpi-info`点击开合,仅新摘要面板做边界定位与限高滚动,点面板正文不触发外层目标链接。
| 1458—1461 | 按目标类型+指标+方向判定适用性;希望月份、剩余月数和来源单独表达;不把多目标估算当资金分配 |

## 二、关键选型

### 选型一 · 多指标如何表示

| 方案 | 用户能感知的结果 | 局限 | 结论 |
|---|---|---|---|
| 在GoalProgress不断追加零散nullable字段 | 可快速展示日期 | 各页面容易自行组合来源与状态,缺一项时再次连带清空其它指标 | 不选 |
| **保留原字段,追加有固定类型的只读观察指标集合** | 每项保留自己的单位/来源/可用状态;列表和详情一致 | 必须约束固定指标类型,不能让模板任意拼数学 | **选择** |
| 公式编辑器、指标注册市场与多条件规则引擎 | 可自由搭建复杂目标 | 引入本期未要求的配置、解释与误用成本 | 不选 |

`GoalIndicator`包含固定kind、单位、类型化value、状态与来源。仅本期需要的进度/缺口/结余ETA/期限对照,不持久化指标目录,不接受用户脚本。GoalProgress的原getter和兼容构造保留,不要求旧消费者同时迁移。

### 选型二 · 偏好存在哪

| 方案 | 对用户配置可靠性的影响 | 局限 | 结论 |
|---|---|---|---|
| 放进family_goal.params_json或retirement_plan.plan_json | 表面无需迁移 | 普通编辑、自动预算、旧程序回滚都可能重新序列化并丢掉未知项;也把新时间与旧投资情景绑在一起 | 不选 |
| **family_goal追加独立可空字段** | 修改主计划保留估算偏好,原行归属/归档/清理机制继续有效,旧程序忽略新列 | 需要一项向后兼容迁移并补SELECT/导出 | **选择** |
| 单独goal_forecast_setting表 | 偏好独立 | 与同一目标一对一,本期不需要独立生命周期;额外的孤儿、导出及删除联动没有给用户增加能力 | 不选 |

只保存来源、手填金额及其币种、希望月份覆盖;不保存当前资产、目标金额、计算日期或完成率。主目标的旧UPDATE不触碰这些新增列,避免“改个名字就丢结余”。

### 选型三 · 结余来源与更新时机

| 方案 | 结果可信度 | 局限 | 结论 |
|---|---|---|---|
| 各目标独立写收入/支出SQL | 可各自取数 | 账户筛选、缺失和开账口径会漂移,同一家庭出现多个月结余 | 不选 |
| **小型共享月结余读取服务,金额只用现有事实层,请求内复用** | 取数窗口及来源可展开核对;改账后立即重读 | 要明确与原投资情景的兼容边界 | **选择** |
| 全局缓存或保存一个月结余快照 | 日期稳定 | 来源改了却不更新,再次要求用户重存目标才能刷新 | 不选 |

新服务只服务本次“仅按结余”指标,不重构旧投资情景或其它收益/支出KPI。复用事实金额和来源证明,不复制金额聚合。

### 选型四 · 时间计算

| 方案 | 解释给用户的含义 | 局限 | 结论 |
|---|---|---|---|
| 缺口÷月结余,整数月向上取整 | 按今天目标金额和月结余不变,多久补齐 | 不是未来购买力或投资复利的预测 | **选择**,与已评审PRD一致 |
| 复用退休复利/通胀情景日期 | 可以考虑回报 | 会把“按当前结余”混成原投资预测,并需要额外回报假设 | 保留为原有独立情景,不作为新ETA |
| 依据目标创建以来的进度斜率推算 | 无需收支来源 | 开账、首次纳入和估值跳动都能造成虚假收入速度 | 不选 |

### 选型五 · 报表如何联动

**选择:实时目标页、列表、仪表盘显示新ETA;报表里的既有“当前计划”条保持原行为,本期不加新ETA。**

不从今天的目标设置臆造旧月的目标设置,也不把当前ETA贴到旧报表。未来若需要完整历史目标预测,需先有计划版本历史,超出本期范围。此处落实PRD“不能混入今日日期”,不改报表主指标或历史AI结果。

## 三、系统概要设计

### 1. 整体设计

```text
既有GoalProgress / 退休View ──────────────┐
family_goal独立估算偏好 ────────────────┼→ GoalForecastService → 纯函数ETA
全家庭事实金额 + 已定稿期 + 来源证明 ──┘                    ↓
                                         只读GoalIndicator集合
                                             ↓
                                   列表 / 详情 / 仪表盘片段
```

### 2. 领域模型

- `GoalForecastPreference`:只含估算偏好。`source=NULL`表示没有覆盖,新退休可读取其已有有效MANUAL结余作为兼容默认,其它情况为AUTO。显式AUTO、手填0、负数与未配置分开。
- `MonthlyContributionWindow`:asOf、本位币、窗口起止、每期收入/支出/完整性、有效月份数、中位净结余及说明。金额可空,真实0保留。
- `GoalForecastBasis`:从既有结果只读映射的当前资金与目标资金、目标身份/类型/方向、观察日;不在这里重新求A/F。
- `GoalCashflowEstimate`:状态、可用时的预计月末与整数月数、采用结余、希望月份和对照差额。
- `GoalIndicator`:固定kind与类型化值(比例/金额/日期与月数)、来源、原因;不会出现一个全局ready控制整个目标。

实际实现采用`Goal`独立偏好字段及`GoalForecastForm`、`MonthlyContributionService.Window/Month`、`GoalForecastService.View/Context`、`GoalCashflowCalculator.Result`承载上述概念,没有为每个概念另建一层类。`AGENTS.md`的L39登记同源与状态边界。

### 3. 类职责与依赖

| 类/位置 | 职责及边界 |
|---|---|
| `GoalCashflowCalculator` | 无DB/时钟/模型的纯函数,传入asOf、A、F、C与希望月份 |
| `MonthlyContributionService` | 用限定家庭、本位币、自然月范围的FactSlice及来源证明产生窗口;不读目标的账户筛选,不写事实 |
| `GoalForecastService` | 适用性、偏好优先级、异常隔离和指标装配;不调用GoalProgressService,避免循环依赖 |
| `GoalProgressService` | 原有主结果先算,之后附加观察指标;computeAll共享本次请求的结余窗口,不改变旧neutralDate含义 |
| `GoalProgressSummary` | 只读同一有效结果拼装小i的公式、实际值与来源;区分R1/R2、指标单位、缺数和报表边界,无查询/写入/模型调用 |
| `GoalForecastService.save` / `GoalMapper` | 按家庭校验与保存独立偏好,与审计同事务;原主配置UPDATE继续不写新增列,新建由原目标服务在同一事务调用 |
| `RetirementController.page` | 从已经取得的View装配,不再为新指标二次查询A/F;草稿用同一份草稿View |
| `GoalForecastController` | 通用目标估算预览/保存,允许字段白名单,不发起AI请求 |
| 目标片段及`goal-estimate.js` | 显示服务端值、行内校验、预览及草稿提示;JS不复制日期公式 |

### 4. 运行架构

仍为同一Spring Boot单体,无新进程、定时任务、外部调用或全局缓存。读操作不触发模型、估值刷新或自动关账。

### 5. 物理架构

不适用 · 不改变部署形态。

### 6. 数据架构

已实现`V80__goal_forecast_preferences.sql`,在备份后应用到beta。family_goal追加:

| 字段 | 默认/语义 |
|---|---|
| `forecast_source VARCHAR(12) NULL` | NULL兼容默认;显式值只有AUTO/MANUAL |
| `forecast_manual_amount DECIMAL(19,2) NULL` | 独立手填月可用结余,0/负值合法;切AUTO保留 |
| `forecast_manual_currency CHAR(3) NULL` | 与手填金额成对,由服务端写当时家庭本位币 |
| `forecast_wish_month CHAR(7) NULL` | YYYY-MM;NULL可表示用户明确不设希望月份 |
| `forecast_wish_override BOOLEAN NOT NULL DEFAULT FALSE` | FALSE继承既有目标日期;TRUE使用独立希望月份(含明确空值) |

约束:来源枚举,手填金额/币种成对,MANUAL必须有金额。应用校验金额绝对值≤10亿元、最多2位小数;年月用YearMonth解析。AUTO不要求金额或运行来源齐全。手填金额的币种不能因切AUTO而被覆盖成另一个币种。

只增列,旧行不填示例数或迁移成MANUAL,不更新旧params_json或retirement_plan。旧程序的SELECT/INSERT/UPDATE列明确列出,忽略新增列,回滚jar可保留偏好。DDL由既有schema_history校验,失败不切jar;迁移中断按现有迁移机制恢复,不手工删新列或重写已发布SQL。

GoalMapper通过公共`COLUMNS`统一覆盖findById、findActive、findActiveByType、findAllByFamily四个读入口;新增专用UPDATE只写估算字段,带`family_id + id + archived_at IS NULL`。影响行0时回读区分幂等同值与无归属,不把“没写进去”报保存成功。

## 四、接口协议设计

### 1. 影响范围

| 入口 | 变化 |
|---|---|
| `/goals`、`/goals/{id}`、`/dashboard` | 在原结果上显示新观察指标,金额和日期按同一结果渲染 |
| `/goals/{id}/retirement`及现有preview | 复用View加入指标,所有原生活/范围/准备金配置保留 |
| `/goals/{id}/estimate/preview`(POST) | 通用目标只读预览,不写偏好/目标/事实 |
| `/goals/{id}/estimate`(POST) | 只保存该目标估算偏好;AUTO缺数据不拒绝 |
| 原新建目标入口 | 可带可选估算偏好,与新目标在同一事务中保存;无该段时旧调用保持兼容 |
| 目标导出/家庭ZIP | 带估算偏好及其币种;当前演算注明观察日/来源,不当历史快照 |
| 报表/历史AI月报 | 不增加新今日ETA、不改变已存结果、不自动重算 |

全部新写入familyId来自认证主体、goalId来自路由,不接受body覆盖。归档、外家庭、不适用目标返回本接口的404空体,不泄露目标存在性;不改变其它旧接口的错误协议。

预览/保存DTO只允许`estimateSource`、`estimateMonthlyAmount`、`estimateWishMonth`和显式覆盖标志`estimateWishOverride`;它们与原退休参数使用不同字段名/绑定白名单。只有用户单独编辑估算希望月份才覆盖;只保存结余继续继承主计划月份,清空则明确不设。非法手填或年月返回字段错误,前端预先同样校验;服务端结果为权威。

### 草稿与保存边界

- 主计划草稿与时间估算草稿各有dirty状态;切tab/显示币种/打开来源不丢值。显示的A/F和ETA必须来自同一主计划版本,禁止拿草稿F配保存版ETA。
- 退休现有预览请求可携带时间估算DTO,服务端用同一草稿View计算;读取/预览均不写任何字段。
- 时间设置保存仅写估算列,不修改生活费、准备金、账户范围、原回报或投资情景开关。HTMX保存后只确认该部分,保留其它尚未保存的主计划输入及提示,不整页重定向冲掉草稿。
- 原投资情景继续使用其已保存投入与回报;新设置有独立名称,不静默改写旧JSON。无新覆盖时可沿用其有效手填投入作为初始参考,来源明确显示。
- 新建目标先完成合法主配置,可选估算偏好与目标同事务写入;AUTO缺来源合法。普通新建/修改接口不强制新增时间配置。无JS退化为服务端表单和字段错误,不由前端制造持久化结果。
- 并发预览以请求序号/取消旧请求丢弃过期响应,不能让较慢旧请求覆盖最新输入。预览不写审计;明确保存成功后记偏好变更审计。

不适用 · 只有现有会话认证内的页面接口,无MCP/Open API能力扩展。

### 3. 上游接口

不适用 · 只读已有数据库事实与设置,不新增行情、银行、模型请求。

## 五、稳定性与质量保障

### 1. 状态与兼容性

判定顺序固定:

1. 不适用目标→不渲染该时间指标,原指标保留。
2. 资金/门槛未知或没有有限门槛→该时间指标待来源/不适用,不清空其它已有值。
3. A≥F→已达成、0个月;结余来源和希望月份不参与这一判定。
4. C未知/手填币种失效→待来源/待核对;不偷换AUTO,不把null当0。
5. C≤0→暂无达成月份,明确零结余或净流出。
6. `N=ceil(max(F−A,0)/C)`。BigDecimal精确求整月,不使用double;先与600比较再转换和加月份,防极小C引发整数/日期溢出。
7. N>600→超过50年,并非永远达不到;否则预计月末=`YearMonth(asOf)+N`。希望月份仅算有方向的月差,不限制能否估算。

金额/比例/日期都来自本位币同一basis。切显示币种只格式化金额,不重新用已舍入的显示值计算N。旧主指标与v1.39.0作零差异比较;旧退休未采用、旧投资情景和旧neutralDate保持原算法。

### 2. 自动来源合同

取`asOf`所在自然月之前6个月,不往前补找“恰好6个有值月”;同时要求期已自然结束及现有已定稿判据。每月的收入/支出来源分别证明,显式填完的零可采用;只有收入或缺支出的月不当作结余。金额只取全家庭本位币`cashflowBreakdown`,不使用目标账户筛选或为退休生活费剔除过的一组消费额。

来源证明沿用RetirementSourceMapper.presence及既有显式填完判据,不能凭一笔流水就宣布缺失的另一侧为0。缺可追溯汇率的月份单独排除并列原因,不把汇率兜底1当来源完整。归档的时间语义继续交给事实层,不按今天成员/账户归档重新求历史金额。

先计算每个有效月的收入−支出,再取中位数;偶数样本均值按HALF_EVEN到分。1—2月可用但注明样本少,0月无来源,不设“必须6月”门槛。周账期自动来源标明不可按周冒充月,允许手填。新服务取数或偏好读取异常仅产生该指标的安全错误状态,主GoalProgress仍可交付。

### 3. 性能

computeAll从原Goal列表已取得偏好,不逐目标查询设置。月结余窗口在本次调用上下文内按家庭/观察日/本位币共享,所有AUTO目标只取一次;不使用跨请求全局缓存。没有适用未达成目标时可不取结余。

禁止在目标循环内新增家庭流水、外部请求或逐月N+1查询。实现阶段对1/3/10个目标比较数据库请求增量,新来源查询次数不随目标数线性增长,不将既有旧算法查询误记为本模块新增。

### 4. 安全与隔离

family_goal已带family_id,新增读写仍在SQL过滤位置限定家庭和有效目标,不只依赖controller校验。金额不写日志,错误只带阶段/目标ID/类别;不要记录表单或原始数据。沿用CSRF、金额隐私和HTML转义,固定原因文案不回显内部异常。

本期新指标不注入既有AI提示词,不改旧报告指纹或触发付费重算。打开页面/预览/保存都不得调用模型或关账。
