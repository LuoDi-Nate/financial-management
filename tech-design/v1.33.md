### 本仓库内的既有事实(决定设计的)

| 事实 | 出处 | 对本版的意义 |
|---|---|---|

| 另有两张表间接挂账户:`holding_allocation`(经持仓)、`holding_import_item`(经截图导入),`fixed_flow_occurrence`(经固定收支) | 同上 | 清单里按「经谁」写子查询 |

| 封板数字不落库,每次打开现算 | `SealedPeriodService` | 删 = 所有含它的月份(含已关账)按新数据重算 —— 正是 D2 要的,不需要「重算」动作 |
| 补录本金(`principal_adjustment`)从事实层进指标:本期收益扣掉、家庭级并进开账基线;**账户第一期归零** | `FactMapper.xml` padj · `FactProjector` | D3 B 的「改记成本金进出」直接写这张表:对方收到 → +X,对方转出 → −X,对方本期损益 = ΔNW − 收支 − 净划转 − 补录本金,**一分不变**;对方那一期是第一期 → 不写(那笔钱自然并进它的开账基线,`openingOf` 里也不再被当成「从别的账户转来」扣掉) |
| `principal_adjustment` 有 `CHECK (amount > 0)`;插入 SQL 要求期是 OPEN | V69 · `PrincipalAdjustmentMapper.insert` | 本金移出是负数 → 放宽成 `amount <> 0`;系统改记要写进已关账的期 → 另加一条系统专用插入(不要求 OPEN、来源固定 `ACCOUNT_DELETE`) |
| 立即备份(v1.32)同步、同一时间一个、两次至少隔 1 分钟 | `BackupNowService` | 删除前先备份;10 分钟内已有一份成功的手动备份就直接用(用户可能刚在备份页点过) |
| 报表「关账于 …」那一行在 `_sealed.html` | `reports/_sealed.html` | 留痕加在它后面 |

### 待实测(阻塞编码)

- [x] MyBatis 注解 SQL 里 `${where}` 替换进来的文本中的 `#{familyId}` 会再被解析成参数(`DynamicSqlSource` 先做 `${}` 文本替换、再解析 `#{}`)—— 通用搬运用得上。

### 静默失败预检

| 可能的静默失败 | 后果 | 怎么让它响 |
|---|---|---|
| 将来加了一张挂账户的表,删除代码没跟上 | 删了还在算(孤儿数据进指标) | 护栏从 `information_schema` 里找出所有 `*account_id*` 列,逐个要求在搬运清单里登记过(或登记为「只改不搬」);单测钉住清单与表结构对得上 |
| 面板说的和实际做的不一致(预演 3 笔,改记了 4 笔) | 用户确认的不是实际发生的 | 预演与真删用**同一份计划**:提交时服务端重算计划、重算确认语,与用户输入逐字比对;中间数据变了 → 确认语对不上 → 不删,面板按新数据重来 |
| 改记方向反了(对方收到的记成本金移出) | 对方收益率被带歪 | 单测按方向逐项断言;e2e 删前删后算对方那一期的损益,逐分相同 |
| 删到一半失败 | 账户没了、划转没改记 | 整个搬运在一个事务里;单测模拟中途失败断言回滚 |
| 恢复时漏插几行 | 恢复后数字不一样 | 搬运清单是同一份,恢复按清单逆序插回;e2e 删 → 恢复后逐表行数与删前相同、对方的补录本金被拿掉 |
| 恢复时对方账户已经没了 | 外键失败整次恢复回滚,或静默跳过 | 逐条检查依赖(期、对方账户、目标、计划、分组)在不在,在的恢复、不在的列出来;对方没了的那笔划转保留改记(不还原) |
| 备份失败还是删了 | 没有后悔药 | 备份失败直接返回原因,事务根本不开始;e2e 走「目录不可写」分支断言库里一行没少 |

## 一、需求分析

### 1. 背景 & 目标

见 PRD §0。技术上要做到的三件事:**看得清**(预演出的东西就是要做的东西)、**删得干净**(21 张表一张不漏,而且将来加表会被护栏逼着登记)、**放得回去**(整块搬走、整块搬回,不在原表里打标记)。

### 2. 需求理解(验收口径)

| FR | 工程判据 |
|---|---|
| FR-1200 / 1201 | 编辑页底部「危险操作」区:「归档此账户」+「删除账户」;账户簿 ⋯ 菜单(PC)与手机行内都有「删除账户…」→ `/accounts/{id}/delete`;任何成员可删,`audit_log` 记名 |
| FR-1210 ~ 1214 | `/accounts/{id}/delete` 是一整页的终端面板(深色、等宽、`$` 命令行;手机上就是全屏);内容来自 `AccountDeletePlanner.plan()`;金额不加 `data-priv` |

| FR-1220 | 先 `BackupNowService.ensureFresh`:10 分钟内有成功的手动备份就用它,否则立即备份一次;失败 → 不删、面板上写原因 |

## 二、关键选型

### 选型一 · 「软删」怎么实现(D1)

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A | 原表加 `deleted_at`,所有读的地方过滤 | 恢复最简单 | **上百条查询**都要加过滤,漏一处就是「删了还在算」—— 本项目「两条路算同一件事只修一条」已经吃过两次亏;PRD §4 明确不做 | 不选 |
| B | 每张表一张影子表(`deleted_cash_flow` …) | 结构化 | 21 张影子表随原表演化,加一列就要两边改,漏了恢复失败 | 不选 |
| **C** | **一张回收站表**:每个被删账户一行,`payload` 存「表名 → 该账户在这张表里的全部行(`SELECT *` 原样)」的 JSON,原表里真删;恢复时按同一份清单把行原样插回(带原 id) | 读路径一行不改(删了就是真没了);新列自动带上(`SELECT *`);原 id 回填,其它表对这些行的引用(如固定收支确认记录指向的流水)恢复后照样对得上 | 恢复要处理「原表结构后来变了」(多了列 → 用默认值;少了列 → 丢掉那个键,按当前表结构过滤) | **选它** |

### 选型二 · 划转怎么改记(D3 B)

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| A · 新增一种「外部进出」流水类型 | 语义直白 | 事实层、报表、体检、导出都要认一种新流水,口径改动面大 | 不选 |
| **B · 写进补录本金(`principal_adjustment`),本金移出 = 负数** | 事实层本来就把它当「外部投入」,对方本期损益 / XIRR / 回撤 / 归因贡献按现有公式自动不变,家庭层面并进开账基线;只放宽一个 CHECK | 用户的补录本金表单仍只收正数(服务端校验不变);老 jar 读负数照样相加,只是时间线上显示成「补录本金 −¥…」 | **选它** |

对方那一期是它的**第一期**(上期没有余额)时不写:事实层第一期的补录本金本来就归零,而那笔钱已经因为划转不在了而整笔进了 `openingOf`(开账基线)。

### 选型三 · 预演与真删的一致性

| 方案 | 劣 | 结论 |
|---|---|---|
| A · 面板算一份展示用的,删除时再按规则做 | 两段代码,迟早不一致(失败模式 ③) | 不选 |
| **B · `AccountDeletePlanner.plan()` 出一份计划(期、计数、逐笔划转与改记方式、确认语);面板渲染它,删除时重算它并逐字比确认语,执行器只按计划里的划转清单改记** | 无 | **选它** |

### 选型四 · 通用搬运放在哪

| 方案 | 劣 | 结论 |
|---|---|---|
| A · `JdbcTemplate` 在服务里拼 SQL | SQL 散在服务层,家庭隔离审计扫不到 | 不选 |
| **B · `AccountTrashMapper` 三个通用方法(`SELECT * FROM ${table} t WHERE ${where}` / 同条件删 / 按列插),表名与条件只来自 `AccountTrashSpec` 里的常量** | `${}` 拼接只接受代码里的常量;单测断言每条条件都带 `#{familyId}` | **选它** |

### 选型五 · 删除前的备份

`ensureFresh`:10 分钟内有一条**成功**且文件还在的手动备份 → 直接用;否则 `runNow`。理由:用户很可能刚在备份页点过(或连删两个账户),再备一次撞「1 分钟间隔」反而删不了;10 分钟之内的数据差异只可能是这个人自己刚做的操作。

## 三、系统概要设计

### 1. 整体设计思路

```
/accounts/{id}/delete ──► AccountDeletePlanner.plan(家庭, 账户)
                            ├ 涉及的期(余额 / 流水 / 划转 / 补录本金)
                            ├ 移走的行数(按搬运清单 count)
                            ├ 逐笔划转:期 · 对方 · 方向 · 金额(对方币种)· 改记方式(补录本金 / 本金移出 / 并进开账基线)
                            ├ 删前 → 删后(事实层:最近已关账期、本期的净资产与钱赚,减掉它自己的那份)
                            ├ 其它(本期最后一个没填 / 计划条目 / 目标 / 默认还款来源 / AI 存稿)
                            └ 确认语
POST /accounts/{id}/delete ─► 重算计划 → 比确认语 → BackupNowService.ensureFresh → AccountTrashService.delete(计划)
                                                                                  (一个事务:存 → 改记 → 置空引用 → 清 AI 存稿 → 删 → 回收站一行 → 审计)
/admin/trash ──► 恢复:AccountTrashService.restore(按清单逆序插回 · 逐条检查依赖 · 拿掉改记写的补录本金 · 还原引用)
            └──► 彻底清除:清空 payload,留元数据(报表留痕还要用)
```

### 2. 领域模型设计

| 概念 | 是什么 | 边界 |
|---|---|---|
| **回收站**(`account_trash`) | 一个被删账户一行:名称 / 类型 / 谁何时删 / 改写的期 / 牵连的划转笔数 / `payload`(各表原行)/ `rewrites`(改记写的补录本金 id、置空的引用)/ 备份文件 / 恢复与清除的时间 | 不进任何计算;彻底清除后只剩元数据 |
| **本金移出** | 负的补录本金,`source_tag='ACCOUNT_DELETE'`,只由删除写 | 用户表单不能写负数;时间线显示「本金移出」;这两类系统改记行用户不能单独删(删了会把对方收益带歪),恢复账户时由系统拿掉 |
| **删除计划** | 预演结果,面板与执行共用 | 只在一次请求里活着 |

### 3. 代码架构设计

| 类 | 职责 |
|---|---|
| `service/trash/AccountTrashSpec` | 搬运清单(表、条件、删除顺序、恢复依赖);**唯一**列出「哪些表挂账户」的地方 |
| `repository/AccountTrashMapper` | 通用搬运 + 回收站表读写 + 预演用的计数 |
| `service/trash/AccountDeletePlanner` | 只读,出计划 |
| `service/trash/AccountTrashService` | 删除 / 恢复 / 彻底清除(各一个事务) |
| `web/account/AccountDeleteController` · `web/admin/TrashController` | 页面与端点 |

### 4. 运行架构

单体不变;删除在请求线程里同步做(先备份几秒~几十秒,再一个事务)。

### 5. 物理架构

不适用。

### 6. 数据架构设计

| 表 | 变化 | 旧行 |
|---|---|---|
| `account_trash` | 新表(V72) | — |
| `principal_adjustment` | `CHECK (amount > 0)` → `CHECK (amount <> 0)` | 不动 |

迁移三问:① 只加表 + 放宽约束;② 回滚 jar:老 jar 不读回收站(删掉的账户在老 jar 下就是没有了,升回来才能恢复);负数补录本金老 jar 照常相加(对方收益不变),时间线显示「补录本金 −¥…」;不需要回滚 SQL;③ 两句 DDL,失败重跑。

## 五、稳定性与质量保障

### 1. 兼容性设计

- 不删任何账户:读路径一行没改,所有页面与上一版逐字相同(零差异基线)。
- 老 jar:见 §三.6。

### 2. 性能评估

删除一个账户:各表按账户 id / 期子查询各一次 + JSON 序列化;一个用了几年的账户(几千笔导入流水)payload 几 MB 以内,存 `LONGTEXT`。一次性动作,不在热路径上。

### 3. 安全性设计

- 任何成员可删(D12),审计记名;确认语服务端重算比对。
- 回收站数据属于家庭数据:进家庭隔离审计;导出 CSV 包不含回收站(PRD §8)。
- 通用搬运的表名 / 条件只来自代码常量,不来自请求。

### 影响矩阵(写操作 × 归属)

| 写操作 | 写了什么 | 归属判据 |
|---|---|---|
| 删除 | 搬走被删账户的全部行;对方账户在**划转发生的那一期**写本金进出(含已关账期) | 事件时点(划转所在的期) |
| 恢复 | 原样插回;拿掉改记写的本金进出 | 原行自己的期 |
| 彻底清除 | 只清回收站 payload | 不涉及账期 |

各页面指标的逐项影响见影响梳理文档第四、五、六节(仪表盘 27 项 / 报表 46 项):被删账户自己的数从所有月份消失;对方账户的数一分不变;家庭层面那几笔划转变成外部资本进出。

## 七、上线与回滚方案

### 1. 可观测

`audit_log`:`ACCOUNT_DELETE`(移走了什么、改记了几笔、备份文件)/ `ACCOUNT_TRASH_RESTORE`(恢复了什么、哪些没恢复)/ `ACCOUNT_TRASH_PURGE`。

### 2. 预案评估
