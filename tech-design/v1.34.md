## 一、需求分析

### 1. 背景 & 目标

见 PRD §0。一个账户里的持仓能按用户自己的顺序排(和平台 App 一致),这个顺序在所有列持仓的地方一致;持仓名称能直接改。

### 2. 需求理解(验收口径)

- 没排过的账户:所有页面顺序与改版前一致(按添加先后)。
- 排过之后:四处展示同一个顺序;之后新加的排最后,其余不动。
- 改名:只动名字;所有显示这只持仓的地方用新名字;券商同步不改回去。

## 二、关键选型

### 选型一 · 顺序存在哪

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | `stock_holding` 加 `sort_order INT NULL` | 一条 `ORDER BY` 就能用;删除账户的搬运清单按整行搬,自动带上;老 jar 忽略这列 |
| B | 单独一张 `holding_order(account_id, holding_id, pos)` | 每处查询都要多 JOIN 一张表;删除账户 / 导出 / 清演示数据 / 隔离审计都要多登记一张表 |
| C | 账户上存一个 id 列表(JSON) | 排序要在 Java 里做,四处取数都得改;持仓增删时列表要同步维护,漏一次就错 |

**为什么不是 B / C**:顺序是持仓自身的一个展示属性,跟着持仓行走最省事;B 和 C 都要在多处额外维护,和「只改一处 `ORDER BY`」比没有任何用户可感知的好处。

### 选型二 · 新加的持仓怎么排到最后

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 新行 `sort_order` 为空;排序规则 `(sort_order IS NULL), sort_order, id` —— 空的排在排过的后面、彼此按添加先后 | 写入入口一个都不用改;没排过的账户全是空 = 按 id,与改版前逐字相同 |
| B | 每个写入入口插入时算 `max(sort_order)+1` | 七个入口都要改,漏一个就插到中间(PRD 失败模式 2);并发插入还要处理同号 |

### 选型三 · 在哪调顺序

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 单独一页 `/accounts/{id}/holdings/order`:一张卡一只 · 拖拽 · 一键排法 · 放下就保存 | 持仓卡片信息多(份额、单价、改份额、归档),单独一页最清楚;手机上就是一列 |
| B | 持仓页上切「排序状态」,把卡片都收成一行 | 同一页两种布局,卡片里的表单在排序状态下要全部藏起来,容易漏 |

页内怎么调,初稿是 ↑ ↓ 置顶 + 保存 / 取消;维护者验收改判为拖拽 —— 选型见下面选型五。

### 选型四 · 改名怎么写库

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 专用语句 `SET display_name = ?`(按家庭、账户、在用过滤) | 只动名字;并发改的份额 / 估值不受影响 |
| B | 读整行、改名、走通用 `update` 写回 | 读到写之间别人(或定时估值)改过的列会被覆盖回旧值 —— 静默错 |

### 选型五 · 拖拽怎么做(验收改判后加 · 2026-10-13)

要的效果(维护者原话):「PC 鼠标可以拖出卡片放到合适的位置,其他卡片要给它让路;手机端也要」。

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | SortableJS 1.15(MIT,约 45KB,随仓库带在 `static/vendor/`,和 htmx / Chart.js 一样不走 CDN)+ 一个共用件 `sort-board.js` | 「卡片浮起来跟着走 + 原位虚线空位 + 其它卡片滑开」是它的核心能力;触屏长按拿起(`delay` + `delayOnTouchOnly`)、拖到边缘自动滚动、动画都是现成的;两页共用一套 |
| B | 浏览器原生 HTML5 拖放(`draggable` + `dragover`) | **手机浏览器基本不支持**(iOS Safari / 安卓 Chrome 的触屏不触发 dragstart)—— 直接不满足「手机端也要」;PC 上拖影是浏览器截的半透明快照,其它卡片不会让路,要自己算位置做动画 |
| C | 自己写(pointer 事件 + FLIP 动画) | 能做到 A 的效果,但长按判定、和页面滚动抢手势、边缘自动滚动、动画中途再次换位,每一样都是用户能踩到的坑;A 已经把这些在大量产品里磨过 |

**为什么不是 B**:手机上用不了,不满足需求。**为什么不是 C**:用户感知到的只有「拖起来顺不顺、手机上会不会误触」,这两样 A 都更稳;C 没有任何用户能感知到的好处。

**交互细节**(落在 `sort-board.js`):

- `forceFallback: true`:PC 也用「卡片跟着鼠标浮起来」的模拟拖动,不用浏览器原生拖影(原生拖影半透明、各浏览器不一样)。
- 手机 `delay: 180` + `delayOnTouchOnly`:长按 0.18 秒才拿起,轻点 / 快速滑动是正常滚页面 —— 初稿「触屏误操作」的顾虑在这里解决。
- **放下就保存**(JSON 接口,`{ok, message}`),提示条带「撤销」(回到上一步并再存一次);失败放回原样。不再有「保存 / 取消」两步:拖拽的心智是「放哪就是哪」,再让人点保存是多一步、也容易忘。
- 账户按成员分组,每组一个独立列表、组间不能互拖(`group.pull/put = false`);保存时按页面顺序把所有组拼成一个完整排列。
- 键盘:卡片可聚焦,Alt + ↑ / ↓ 移一格(无障碍)。

### 选型六 · 账户顺序存哪(验收时加)

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 复用已有 `account.display_order`,保存写 10 / 20 / 30 … | 账户簿、填报页、仪表盘本来就按它排,一行不用改;留间隔,编辑页手填一个数字也能插进去 |
| B | 新加一列专门给拖拽用 | 两个顺序键谁优先说不清;所有按 `display_order` 排的地方都要改 |

## 三、系统概要设计

### 1. 整体设计思路

- 顺序:`StockHoldingMapper.ACCOUNT_ORDER` 一个常量,两条按账户取持仓的查询共用;保存 = `StockHoldingService.saveOrder`(校验完整排列 → 写 1..n)。
- 改名:`StockHoldingService.rename`(归一化 + 校验)→ `StockHoldingMapper.updateDisplayName`;控制器改完清资产透视缓存。

### 2. 领域模型设计

`StockHolding.sortOrder`(Integer,可空)。不参与任何计算。

### 3. 代码架构设计

| 层 | 文件 | 做什么 |
|---|---|---|
| 迁移 | `V73__holding_sort_order.sql` | 加列 |
| Mapper | `StockHoldingMapper` | `ACCOUNT_ORDER`;两条按账户的查询改用它;`updateSortOrder`;`updateDisplayName` |
| Mapper | `AccountMapper` | `updateDisplayOrder`(按家庭 + 在用过滤) |
| Service | `StockHoldingService` | `saveOrder`(完整排列校验)· `rename`(去首尾空格、并空格、非空、≤ 64、同账户在用) |
| Service | `AccountService` | `saveOrder`(全部在用账户的完整排列 → 10 / 20 / 30 …) |
| Web | `StockHoldingController` | `GET /accounts/{id}/holdings/order` · `POST …/order/save`(JSON)· `POST /accounts/{id}/holdings/{hid}/rename` |
| Web | `AccountController` | `GET /accounts/order` · `POST /accounts/order/save`(JSON) |
| 前端共用件 | `static/vendor/Sortable.min.js` · `static/js/sort-board.js` · `style.css` 的 `.sort-*` | 拖拽、让路动画、手机长按、放下即存、撤销、一键排法、键盘 |
| 页面 | `stock/holdings.html` · `stock/holding-order.html` · `accounts/order.html` · `accounts/index.html` | 持仓列表头上「调整顺序」(≥ 2 只才出现)· 卡片「改名」· 两个排序页 · 账户簿顶上「调整顺序」 |

### 4. 运行架构 / 5. 物理架构

不适用 · 无新进程。新增一个前端库 SortableJS(MIT,文件随仓库带,不走 CDN —— 和既有 htmx / Chart.js 同一做法,国内网络和离线 Docker 都不受影响)。

### 6. 数据架构设计

`stock_holding.sort_order INT NULL`。不建索引(按账户取的持仓通常十几行)。删除账户的搬运清单按 `SELECT *` 整行搬,恢复时原样插回,新列自动带上;导出 CSV 不含这一列(展示属性)。

## 五、稳定性与质量保障

### 1. 兼容性设计

没排过的账户 `sort_order` 全空,排序规则退化成 `ORDER BY id`,与改版前逐字相同。回滚 jar:老 jar 不读新列,顺序回到按添加先后;改过的名字照常显示。

### 2. 性能评估

`ORDER BY` 多两个表达式,作用在单个账户的十几行上,可忽略。保存顺序 = n 条单行 UPDATE,在一个事务里。

### 3. 安全性设计

所有写语句按家庭(经账户)+ 账户 + 在用过滤;保存只收这个账户自己的在用持仓。账户顺序按 `family_id` + 在用过滤,只收本家全部在用账户。名称是纯文本,Thymeleaf 转义输出;拖拽件只读 `data-*` 属性、不拼 HTML。

### 影响矩阵(写操作 × 归属)

只有三个写操作(持仓顺序、账户顺序、改名),都不碰任何金额与账期,不进指标。

## 附录一 · 实施记录(2026-10-13)

1. **改名的浮层**:第一版把输入框直接展开在标题行里,PC 上把「保存」挤成竖排两个字 —— 截图看出来的。改成 PC 上浮在标题下面(不挤动标题行)、手机上整行展开(浮层在窄屏上会出右边界)。
2. **资产打标页的「账户内现金」**照旧在上面单列(系统归类、不可标),其余持仓按保存的顺序;e2e 只比非现金那几行。
3. **「调整顺序」入口挪位置**(维护者验收:「排序是哪里?我怎么都没看到」):第一版放在持仓页操作栏一排「+ 添加持仓 · …」按钮的最后,看上去像又一个添加按钮,被一排同样的框淹没。挪到持仓列表头上(「持仓 · N 只」那一行右边,实心按钮)—— 用户想排列表时眼睛就在列表上。手机上提示文字收短,按钮不折行。
4. **账户编辑页「危险操作」**(v1.33 的块,本版顺手重做):维护者指出按钮丑、没对齐 —— 两行 flex「按钮 + 说明」,按钮宽度不同让说明起点错开。改成共用件 `.danger-zone`(grid 两列 · 按钮同宽同高 · 说明同一列起),flow 49 加同尺寸 + 对齐断言;规约写进 `docs/visual-spec.md`「操作行 / 按钮组」。
5. **↑ ↓ 改拖拽 + 账户也能排**(维护者验收:「这个交互也过于丑陋了 —— 要支持拖拽来互换位置,其他卡片要给它让路,手机端也要;账户也要用类似的逻辑」):选型见二、选型五 / 六。排序页从「一行 + 三个小按钮 + 底部保存」改成「一张卡 + 拖动把手」,放下就存、提示条撤销。e2e flow 51 用真鼠标事件拖、用 CDP 真触屏事件长按拖(Playwright 没有触屏拖动的 API),断言页面顺序 + 库里的顺序列。
6. **双端截图自查后两处版式**:① 手机上持仓排序页标题「富途证券-港美股 · 持仓顺序」折成「…持仓顺 / 序」、说明被右边「完成」挤成窄条 —— 标题改成「持仓顺序」,账户名放标题下一行小字(长名字省略号截断),说明整行放到标题行下面;账户排序页同一版式。② 一键排法三个按钮宽度不一、手机上折成两行 —— 改成同宽同高(PC 每个 9.5rem;手机一行三等分),flow 51 加同尺寸 + 同一行 + 文字不截断断言。

## 附录二 · v1.34.1 部署防卡死(2026-10-14)

### 根因

v1.34.0 首次部署(13:51:22 起)卡在 `deploy.sh` 第 11 步 `mvn package`:
- **证据**:阿里云「系统盘读写带宽达上限」(14:15 起)· 读 107MB/s、写 ~20KB/s、CPU 25% · 14:02 起 app 拿不到 DB 连接(Hikari)· snapd / journald 启动超时 · SSH 握手超时。
- **机制**:prod 2 核 3.5G,常驻 app ~0.3–0.7G + MySQL ~0.4G + 同机微信网关 ~0.45G+ + 富途 OpenD ~0.1G;本机编译(mvn 默认堆 ≈ 1/4 内存)把匿名内存顶满。`/etc/sysctl.conf` 里 `vm.swappiness = 0`(阿里云镜像默认)→ 内核不换出空闲匿名页,改为反复丢弃程序代码页再从盘读回 —— **只读不写**的页缓存抖动,ESSD Entry 带宽被读打满,全机停摆;有 2G swap 兜着、可回收的文件页一直有,所以不触发 OOM,永远不会自己好。
- **为什么前一天没事**:v1.33.0 部署时(15:23–15:36)snapd 也超时过 —— 当时已在临界点;那时机器才开机 4 小时,当天开机 26 小时。
- **没有直接证据的部分**:sysstat 当时没开,拿不到卡死前的内存曲线;「常驻 + 编译超出内存」由「只读不写 + swappiness=0 + 重启后实测各进程占用 + 限堆后编译只吃 ~370MB 就顺利完成」推出。

### 选型

**不在 prod 上编译**

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 发布时在 beta 用同一个 tag 编 jar → scp → sha256 对上 → `deploy.sh --jar`(再核对 jar 版本 == 检出版本) | prod 上零编译内存;beta 本来就编同一份代码;两道核对保证换上去的就是这个 tag |
| B | 从 GitHub Release / GHCR 拉 CI 编好的 jar | prod 在国内,GitHub 附件下载不稳;要 CI 额外产出 jar |
| C | 仍在 prod 编,只加内存保护 | 保护能防卡死,但部署会因内存不够被拦下(prod 常驻已占大半),变成「部署不了」 |

**为什么不是 B**:下载不稳会让发布时好时坏,而 beta → prod 的 scp 一直稳。**为什么不是只有 C**:C 作为自部署用户的默认路径和 `--build-on-prod` 兜底保留,但对 prod 来说「拦下」不等于「能部署」。

**本机编译的保护**:编前查 `MemAvailable`(默认 ≥ 1000MB)· `MAVEN_OPTS` 默认 `-Xmx768m`(用户设了就用用户的)· 看门狗每 3 秒采样,**连续两次** < 300MB 才停(单次抖动不误杀),用 `setsid` 让编译自成进程组、停时整组停(mvn 若派生子进程不会成孤儿)。阈值保守:限堆后实测编译只吃 ~400MB。

**部署脚本在 prod 后台跑**:以前 `ssh … sudo bash deploy.sh` 前台跑,SSH 一断(这次是控制台重启)deploy.sh 跟着被挂断。改为 `setsid nohup` 后台跑、写日志文件和退出码文件,本地每 10 秒拉增量日志;SSH 加 `ServerAliveInterval=15 / CountMax=4`,prod 卡死时 1 分钟内断开并提示「无响应」,而不是挂一个半小时没消息。
