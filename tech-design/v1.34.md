## 一、需求分析

### 1. 背景 & 目标

见 PRD §0。一个账户里的持仓能按用户自己的顺序排(和平台 App 一致),这个顺序在所有列持仓的地方一致;持仓名称能直接改。

### 2. 需求理解(验收口径)

- 没排过的账户:所有页面顺序与改版前一致(按添加先后)。
- 排过之后:四处展示同一个顺序;之后新加的排最后,其余不动。
- 改名:只动名字;所有显示这只持仓的地方用新名字;券商同步不改回去。

---

## 二、关键选型

### 选型一 · 顺序存在哪

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | `stock_holding` 加 `sort_order INT NULL` | 一条 `ORDER BY` 就能用;删除账户的搬运清单按整行搬,自动带上;老 jar 忽略这列 |
| B | 单独一张 `holding_order(account_id, holding_id, pos)` | 每处查询都要多 JOIN 一张表;删除账户 / 导出 / 清演示数据 / 隔离审计都要多登记一张表 |
| C | 账户上存一个 id 列表(JSON) | 排序要在 Java 里做,四处取数都得改;持仓增删时列表要同步维护,漏一次就错 |

**为什么不是 B / C**:顺序是持仓自身的一个展示属性,跟着持仓行走最省事;B 和 C 都要在多处额外维护,和「只改一处 `ORDER BY`」比没有任何用户可感知的好处。

### 选型二 · 新加的持仓怎么排到最后

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 新行 `sort_order` 为空;排序规则 `(sort_order IS NULL), sort_order, id` —— 空的排在排过的后面、彼此按添加先后 | 写入入口一个都不用改;没排过的账户全是空 = 按 id,与改版前逐字相同 |
| B | 每个写入入口插入时算 `max(sort_order)+1` | 七个入口都要改,漏一个就插到中间(PRD 失败模式 2);并发插入还要处理同号 |

### 选型三 · 在哪调顺序

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 单独一页 `/accounts/{id}/holdings/order`:一行一只 · ↑ ↓ 置顶 · 一键排法 · 保存 / 取消 | 持仓卡片信息多(份额、单价、改份额、归档),单独一页最清楚;手机上就是一列 |
| B | 持仓页上切「排序状态」,把卡片都收成一行 | 同一页两种布局,卡片里的表单在排序状态下要全部藏起来,容易漏 |
| C | 拖拽 | 触屏长列表误操作多、无障碍差(PRD §4 已排除) |

### 选型四 · 改名怎么写库

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 专用语句 `SET display_name = ?`(按家庭、账户、在用过滤) | 只动名字;并发改的份额 / 估值不受影响 |
| B | 读整行、改名、走通用 `update` 写回 | 读到写之间别人(或定时估值)改过的列会被覆盖回旧值 —— 静默错 |

## 三、系统概要设计

### 1. 整体设计思路

- 顺序:`StockHoldingMapper.ACCOUNT_ORDER` 一个常量,两条按账户取持仓的查询共用;保存 = `StockHoldingService.saveOrder`(校验完整排列 → 写 1..n)。
- 改名:`StockHoldingService.rename`(归一化 + 校验)→ `StockHoldingMapper.updateDisplayName`;控制器改完清资产透视缓存。

### 2. 领域模型设计

`StockHolding.sortOrder`(Integer,可空)。不参与任何计算。

### 3. 代码架构设计

| 层 | 文件 | 做什么 |
|---|---|---|
| 迁移 | `V73__holding_sort_order.sql` | 加列 |
| Mapper | `StockHoldingMapper` | `ACCOUNT_ORDER`;两条按账户的查询改用它;`updateSortOrder`;`updateDisplayName` |
| Service | `StockHoldingService` | `saveOrder`(完整排列校验)· `rename`(去首尾空格、并空格、非空、≤ 64、同账户在用) |
| Web | `StockHoldingController` | `GET/POST /accounts/{id}/holdings/order` · `POST /accounts/{id}/holdings/{hid}/rename` |
| 页面 | `stock/holdings.html` · `stock/holding-order.html` | 操作栏「调整顺序」(≥ 2 只才出现)· 卡片「改名」· 排序页 |

### 4. 运行架构 / 5. 物理架构

不适用 · 无新进程、无新依赖。

### 6. 数据架构设计

`stock_holding.sort_order INT NULL`。不建索引(按账户取的持仓通常十几行)。删除账户的搬运清单按 `SELECT *` 整行搬,恢复时原样插回,新列自动带上;导出 CSV 不含这一列(展示属性)。

## 五、稳定性与质量保障

### 1. 兼容性设计

没排过的账户 `sort_order` 全空,排序规则退化成 `ORDER BY id`,与改版前逐字相同。回滚 jar:老 jar 不读新列,顺序回到按添加先后;改过的名字照常显示。

### 2. 性能评估

`ORDER BY` 多两个表达式,作用在单个账户的十几行上,可忽略。保存顺序 = n 条单行 UPDATE,在一个事务里。

### 3. 安全性设计

所有写语句按家庭(经账户)+ 账户 + 在用过滤;保存只收这个账户自己的在用持仓。名称是纯文本,Thymeleaf 转义输出。

### 影响矩阵(写操作 × 归属)

只有两个写操作(保存顺序、改名),都不碰任何金额与账期,不进指标。
