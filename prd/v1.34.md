## 0 · 这一版在解决什么

**背景与现状**:

1. 一个账户(券商、基金、理财……)里的持仓,所有页面都按**添加的先后**排(`stock_holding.id`),没有任何地方能改。账户本身有「显示顺序」(编辑页的数字),持仓没有。
2. 每月核对余额时,用户是对着平台 App 一行一行看的 —— 平台有自己的排法(多数按市值从大到小,也有按自选顺序的)。两边顺序不一样,就得在十几只持仓里来回找,10 分钟的预算有一部分花在「找」上。
3. 同一份持仓列表出现在好几个地方:持仓管理页、填报页「股票收入」选账户后联动出的持仓、截图导入的「旧持仓」那一侧、资产打标页。只改一处的话,用户在别处看到的还是旧顺序。

**服务谁**:每月核对持仓的家人。

**主推动力**:**让持仓的顺序和平台对得上,核对时从上往下挨个对**。

**顺带(#41)**:持仓名称填错了没地方改(账户名能在「编辑」里改,持仓不行),只能新加一只再归档旧的。名字也是截图导入「新旧比对」认同一只的依据之一 —— 改成平台 App 上的名字,下次导入就能对上。

## 1 · 调研

初稿参照常见 App 的「编辑顺序」模式(进入排序状态 → 上下移 / 置顶 → 保存),手机不做拖拽。**维护者验收时改判**(2026-10-13):「这个交互也过于丑陋了 —— 要支持拖拽来互换位置,PC 鼠标可以拖出卡片放到合适的位置,其他卡片要给它让路,手机端也要;账户也要用类似的逻辑支持可视化的排序」。

改成主流看板 / 列表 App 的做法(Trello、Notion、iOS 提醒事项的编辑列表):

- PC:按住卡片拿起,卡片浮起来跟着鼠标走,原位置留一个虚线空位,其它卡片**滑开让路**;松手落位。
- 手机:**长按**拿起(轻点 / 快速滑动是正常滚页面 —— 这就是初稿担心的「误操作」的解法),拖到屏幕边缘自动滚动。
- 每次放下就保存,底部提示条上能「撤销」(不再有「保存顺序 / 取消」两步)。
- 无障碍:选中一行按 Alt + ↑ / ↓ 也能移。

## 4 · 不做什么

- **不做「每次自动按市值排」**:市值每天变,顺序跟着跳,和「对着平台一行行看」反而对不上(平台的自选顺序也不跟市值走)。要按市值,点一次「按市值从大到小」再保存。
- ~~不做拖拽~~(验收时改判,见 §1)。不做持仓**跨账户**拖(持仓属于哪个账户不是顺序问题);不做账户**跨成员组**拖(那是改主理人,去编辑页改)。
- **不改任何金额、口径**:只是展示顺序。

## 9 · 失败模式(pre-mortem)

1. **只改了一处列表**:持仓页按新顺序,填报页 / 截图导入还是旧顺序 —— 用户以为没存上。
   **怎么发现**:持仓列表的取数收口到一个排序规则;e2e 保存顺序后依次打开四处,断言顺序一致。
2. **新加的持仓插到中间**,把用户排好的顺序打乱。
   **怎么发现**:单测 + e2e:保存顺序后再加一只,断言它在最后、其余不动。
3. **排序把已归档的持仓也排进来**(或保存时漏掉一只,顺序出现空洞)。
   **怎么发现**:保存只接受这个账户全部在用持仓的完整排列(少一只、多一只、别的账户的都拒绝)。
5. **手机上滑页面被当成拖动**,一滑顺序就乱了(初稿不做拖拽的原因)。
   **怎么发现**:长按 0.18 秒才拿起、轻点 / 快速滑动照常滚动;e2e 用真触屏事件长按拖一次,断言顺序和库都变了。
6. **账户拖进别的成员组**,看起来像换了主理人、实际只改了顺序。
   **怎么发现**:每个成员组是独立列表,组间不能互拖;服务端照样只收全部在用账户的完整排列。
4. **改名顺手把别的列也写了**(走通用的整行 update,把并发改过的份额 / 估值覆盖回旧值)。
   **怎么发现**:改名走只写名字这一列的专用语句;e2e 断言改名前后份额 / 估值 / 代码 / 行业标逐字相同。

## 附录 · v1.34.1 部署不再把服务器拖死(2026-10-14)

> 状态:**已发布 · v1.34.1**(2026-10-14 · 首次用新流程发布:beta 编 jar → scp → prod `deploy.sh --jar`,prod 端 31 秒)· 维护者 2026-10-14「非可选的优化全部做掉」 · 技术附录见 [`tech-design/v1.34.md` 附录二](../tech-design/v1.34.md)

### 0 · 解决什么

2026-10-14 发 v1.34.0 时,部署脚本在 prod 服务器本机编译新版本,和线上服务、MySQL、同机别的常驻进程一起把 3.5G 内存用光;服务器卡死约 100 分钟(网页、SSH 全超时),最后靠云控制台强制重启。重启后用「暂停同机大进程 + 限制编译内存」才部署成功。

暴露了四件事:**编译不该在线上机器做**(或至少要有保护)· **编译放在数据库迁移后面**(编不出来时库已经改了)· **失败后照规程回滚会把线上换成更老的版本**(新 jar 根本没换上去)· **部署输出没有时间**(卡住时看不出卡在哪一步、卡了多久)。

### 3 · FR

| # | 要求 |
|---|---|
| FR-1340 | 发布流程不在 prod 上编译:在测试机用同一个 tag 编好 jar,传到 prod,两边文件指纹一致才继续;部署脚本再核对 jar 里的版本号和服务器上检出的版本一致,对不上什么都不动。 |
| FR-1341 | 在服务器本机编译(自部署用户的默认做法)时:编译前可用内存不到 1000MB 就停下,说清楚「线上没动 + 可以怎么办」;编译限制内存;编译期间可用内存连续两次低于 300MB 就停掉编译 —— 都发生在换程序之前,线上继续跑旧版。阈值可调,确认要硬编可以强制。 |
| FR-1342 | 编译(或核对预编译 jar)放在数据库迁移之前:编不出来 = 库没改、线上原样。 |
| FR-1343 | 回滚前核对线上当前版本:不是本次发布的版本(说明新 jar 没换上去)就拒绝,什么都不动;可以只问「现在能不能回滚」而不动任何东西。 |
| FR-1344 | 部署每一步打开始时间和上一步用时,全程输出另存一份日志文件。发布时部署脚本在 prod 后台跑,网络断了它照跑;本地定时拉日志,prod 连不上时提示「无响应 N 秒」,恢复后补齐日志、拿到结果。 |

服务器配置(不进代码,已在 prod 上改,记在这里备查):`vm.swappiness` 0 → 10(内存紧时先换出闲置内存,而不是反复从盘读回程序代码)· 打开 sysstat 采集(下次有内存 / 磁盘历史可查)· 系统日志上限 1G(原 3.8G,磁盘 81% → 74%)。

### 4 · 不做什么

- **不装自动杀进程的守护(earlyoom)**:可选项,维护者未要;部署本身的看门狗已兜住编译这一类。
- **不做「编译前后自动停 / 启同机服务」的钩子**:可选项,未要。
- **不改 Docker 部署**:Docker 镜像在 CI 里编译,服务器上不编译,不受这次影响。
- **不动同机微信网关**:它的重连死循环刷日志是它自己的问题,归维护者裁。

### 3 · 改法(待拍板)

**第 1 条(已定:按建议改)**:新账户第一期的开账基线再扣掉「这一期挂在这个账户上的收入 − 支出」。例:从 A 转进 1,000、记了 200 工资、期末 1,200 → 开账基线 0(原来是 200);期初本来有 500、这期从它花了 100、期末 400 → 开账基线 500(原来是 400)。资产类不为负(扣出负数说明这期亏了,留在钱赚里)。同一个函数改一处,家庭开账基线 / 本月资产收益 / 钱赚 / TWR / XIRR / 财富水位 / 归因瀑布 / 账户表累计净投入 / 封板「资本纳入」一起对。没挂账户的收支(按人填总数)照旧分不出来、不动。

**第 2 条(已定:每次问,默认 A)**:往「之后已经有人确认过余额」的历史期里记划转 / 挂账户的收支时,记之前问一句:

| 选项 | 做什么 | 适合 |
|---|---|---|
| **A · 只补记这笔,余额不动**(建议默认) | 只记流水 / 划转,不改这一期和之后的余额 | 当时填的余额是对着 App 看的、已经包含了这笔 —— 只是当时忘了记。补上之后,「凭空亏了 / 赚了」就被解释掉了 |
| **B · 当时的余额还没算上它** | 改这一期的余额,并把之后**每一期**(含已关账)这个账户的余额都挪同样的数 | 当时的余额本来就漏了这笔(比如新账户的历史是现在才补的) |

**什么时候问(实施时收紧,判据写死在一处)**:这个账户**这一期的余额是有人确认过的**(不是系统代填的延续值),**并且之后已经开始的期里也有确认过的余额**(还没开始的期不可能有「当时看到的余额」,那只能是预建 / 测试数据,不算)。两条缺一不可 —— 这一期的余额还没填 / 是系统代填的,它就不是「当时看到的数」,照旧把这笔加上去才对(之后确认过的余额是真实观察,本来就包含它);之后没有确认过的余额,照旧「改这一期 + 传导到下一个系统代填的期」。所以双活跃窗口里进行期还是系统代填时,不弹、照旧传导。

**删一笔**:按这一笔当初记的方式撤回 —— B 记的,这一期和之后各期一起挪回去;A 记的(或当初是普通记账、现在两头都确认过了),只撤记录、余额不动。删除确认框的话术跟着改成这一句。

**不开 JS / 没选**:服务端按 A 处理(默认),所以弹框只是「问」,不会因为没问到就把确认过的余额改坏。

**第 3 条(已定:按建议改)**:已关账的月份,「应填」不算「那个月结束之后才建、而且那个月没有快照」的账户。在那个月补过余额的照样算(补过就是填了)。

**第 5 条(已定:保留实时,改测试和文档)**:仪表盘这一格维持 v1.10 的「当月实时」(你当时定的:显示真实值 + 说明口径);改 flow 21:估值刷新后**报表页**锚定稿期的收益不许动(真规则),仪表盘这一格的变化必须**正好等于**净资产的变化(估值只动存量,不许动收支)—— 确定可复现,不再看行情脸色。v1.23 矩阵第 10 行注明「仪表盘是实时值,E 列 ↑」。
  - 另一个选项:补录期没关账时让仪表盘这一格也冻住 —— 推翻 v1.10 的决定,不建议。

### 4 · 不做什么

- 不改双活跃窗口里补录期 / 进行期的余额传导(v1.23 FR-623)。
