## 0 · 这一版在解决什么

### 背景与现状

三条诉求看起来不相干,底下是同一件事:**系统自己知道、但没告诉用户的东西**。

| 系统知道 | 用户看到 |
|---|---|
| 你上个月确认过的余额,刚被这个月的一次收入改动改掉了 | 什么都没有 |
| 你有十几个活期账户,它们之间的划转对「家里有多少钱」毫无意义 | 归因里十几条互相抵消的噪声 |
| 归因在回答「这个月钱变了多少、是谁造成的」 | 一句「没有录入」 |

**这不是「体验不够好」,是三处明确的信息缺口** —— 每一处都有具体的、可复现的现象在下面。

### 服务谁

**主要受益者:自建用户与维护者本人**(会主动改数据、会看归因的那类)。
非技术家人间接受益 —— 分组 A 的提示让她们不会在不知情的情况下推翻已确认的数。

### 主推动力

**分组 A(别让一次改动悄悄推翻上一次的确认)是主推动力。**

它是唯一一条「用户已经因此付出了真实代价」的:提交者为此**把上个月账期重新打开重填了一遍**。
分组 B 和 C 是同一次反馈里顺带解决的,不是这一版存在的理由 ——
如果时间只够做一件事,做 A。

### 本版新引入的名词

| 名词 | 含义 |
|---|---|
| **余额校准状态** | 某账户在某期「本月余额有没有被人确认过、什么时候确认的」。它不是新数据,是把已有的 `period_snapshot` 提交时间**显式说出来** |
| **活期合并视图** | 一个**纯展示层**的聚合体:把标为「随时可取」的账户在统计侧合并成一个。底层数据不动 |

其余名词(镜头 / 开账基线 / 人赚钱赚 / 定格 / 随时可取)见 `AGENTS.md` 领域概念节,这里不重复。

## 2 · 用户故事

**全部引用提交者原话。**

### 第 1 条 · 收入与余额校准的先后关系

> 「一旦后期二次修改收入,错过或者影响了这个先后关系,或者没有重新去校验余额,就会导致**已经校准的余额失效**!
> ……我觉得至少有个强烈的提醒……因为校验后的余额一般来说,实际上一旦录入一次就不会再变更了,
> 或者说是它的**稳定性比收入的录入要高**。」

> 「而且对于这种修改之前已关闭月份的场景,好像计算有问题……
> 因为我把之前的数据修改后,在仪表盘上查看,**始终好像还是之前的数据**,并没有更新。」

**照他的路径在 beta 上用真实浏览器复现过**(重开上月 → 删一笔收入 → 重录一笔金额不同的 → 重新关账):

| 他以为 | 实际 |
|---|---|
| 已校准的余额「失效」 | **被直接改掉了** —— 期末余额跟着那笔收入同步变化,页面零提示 |
| 仪表盘数字没更新 | **更新了** —— 没更新的是 AI 复盘那段解读(已在 v1.19.16 修掉) |

复现还坐实了一个**他没提、但一定会让人困惑**的条件:

> **当月还没填余额的账户,它上面的变动不会进「本期净资产变化」。**
> 复现时删掉的那笔落在一个当月未填余额的账户上(19 个账户填了 18 个),
> 于是它对仪表盘毫无影响。**「改了数据但数字不动」确实会发生**,而页面没有解释这个条件。

**他那句「校验后的余额稳定性比收入录入高」是这一版的设计原则** ——
提示该保护的是**后确认的那个**,不是先录的那个。

### 第 2 条 · 活期账户按总计统计

> 「由于这些划转相对频繁且多,所以不可能或者说不方便在账户金额校验的时候,把这些所有的划转全部有效地输入进去,
> 这就类似于支出的流水账的录入了,我觉得这是很难甚至是不可行的。所以我建议,
> 是否可以将所有活期账户在**录入时仍然按账户录入,但在最终统计收益、计算等场景下汇总展示**。
> 这实际上跟把当前已有的设计——所有支出都仅记录到一个总额在一定程度上是一个道理。」

**这个类比是准的。** 它和「支出只记一个总额」同源:**不让录入负担跟着账户数量线性增长**。

### 第 4 条 · 归因看不懂

> 「最后就是那个什么归因……这个归因确实没搞明白怎么修改或者怎么玩。
> 反正看着**显示没有录入**,也不知道怎么改,能否简化/新增入口或加点什么指导之类的?」

一个需要看文档才会用的功能,等于没做。

## 3 · FR

**preview**:[`preview/v1.20/index.html`](../preview/v1.20/index.html)(已双端真浏览器渲染核对)

### 分组 A · 别让一次改动悄悄推翻上一次的确认

| # | 要求 |
|---|---|
| FR-450 | 在**当月已校准过余额**的账户上新增 / 删除 / 修改收支时,**当场**告诉用户:这个账户的余额是什么时候校准的、这笔改动会把它从多少改成多少 |
| FR-451 | 提示里要给**下一步**,不是只给警告 —— 至少「知道了,余额按新值走」和「去重新校准这个账户」两条路 |
| FR-452 | 账户在填报页上要能**一眼看出**「本月余额校准过没有 / 什么时候校准的」,不用点进去 |
| FR-453 | **当月未填余额的账户,其变动不进「本期净资产变化」** —— 这个条件必须写在页面上。当用户改的恰好是这类账户时,要主动说明 |
| FR-454 | 重新打开已关账月份时,提示要**列出会被重算的东西**,而不是只说「会重算之后所有指标」 |

### 分组 B · 活期账户可以合起来看(可选 · 默认关)

| # | 要求 |
|---|---|
| FR-460 | 提供开关「把活期账户合并统计」,**默认关闭** |
| FR-461 | **录入侧完全不变** —— 仍然按账户填余额、记收支。合并只发生在统计与展示侧 |
| FR-462 | 开启后,被判定为「随时可取」的账户在**收益计算 / 归因 / 透视 / 分布**里合并成一个聚合体 |
| FR-463 | 「哪些账户算活期」必须**用户可见、可改**。复用现有流动性分层,不新造概念,**不做自动判定** |
| FR-464 | 合并是**纯展示层**:底层数据一行不动,随时可关,关掉立刻恢复 |
| FR-465 | 页面要说清**代价**:合并之后这几个账户之间的收益差异、单账户归因就看不到了 |

### 分组 C · 归因要能自己看懂

| # | 要求 |
|---|---|
| FR-470 | 归因区**空态**要说清三件事:它在回答什么问题、为什么现在是空的、下一步做什么 |
| FR-471 | 用一句话解释归因在回答的问题,放在功能旁边,不放文档里 |
| FR-472 | 入口要在用户会经过的路径上,而不是要找 |

### 关键文案(文案即功能)

| 场景 | 文案要点 | 为什么这句话本身就是功能 |
|---|---|---|
| FR-450 提示 | 「这个账户的余额在 **MM-DD 校准过**,这笔改动会把它变成 **X**」 | 少了「校准过」三个字,用户不知道自己在推翻什么 |
| FR-453 提示 | 「这笔改动**不会**反映到本期净资产变化 —— 该账户本月还没填余额」 | 这一句就是提交者困惑的解药 |
| FR-465 代价 | 「合并后,这几个账户**各自的收益差异看不到了**」 | 不说清就是把取舍藏起来 |
| FR-470 空态 | 「这块在回答:这个月家里的钱变了多少,分别是哪些账户、哪类资产造成的」 | 这一句就是 FR-471 本身 |

**不画。** preview HTML 已覆盖全部交互。
唯一的状态机(账期开/关/重开)是既有行为,本版只改它的**提示文案**(FR-454),不改状态转移。

## 4 · 不做什么

### 非目标

- **不做自定义支出分类 / 支出报表** —— 已拆到 [#18](https://github.com/LuoDi-Nate/financial-management/issues/18) 独立设计
- **不改默认口径** —— 分组 B 全部行为在开关后面
- **不加二次确认弹窗** —— 分组 A 是**提示**,不是审批。用户是家里人,不是审批流
- **不动账期状态机** —— FR-454 只改文案

### 撞上「刻意不做」清单的

**分组 B 贴着「逐笔流水账」这条边,但没有越过。**

提交者要的**恰恰相反**:他说「把所有划转录进去……很难甚至是不可行的」,
所以他要的是**少录**(合并统计),不是多录。**方向与清单一致,不是例外。**

原 issue 第 3 条确实撞上「消费品类细化」——**已剥离到 #18**,不在本版。

## 6 · 存量影响

| 维度 | 这一版的影响 |
|---|---|
| **schema** | 分组 A / C **零 schema 改动** —— 校准状态是把已有 `period_snapshot` 的提交时间显式读出来,不新增字段。分组 B 需要**一个开关**存进 `family_runtime_config`(既有 KV 表,只加行不加列) |
| **口径** | 见下 |
| **UI** | **没开分组 B 的用户,统计/归因/透视一个像素都不变。** 分组 A / C 会新增提示与空态文案 —— 属于**只增不改**:不改任何既有数字与布局 |

### 口径变更声明

**分组 A / C:本版不涉及口径变更。**

**分组 B:涉及,但只在开关打开时生效。**

- **改了什么**:开启后,「随时可取」的账户在收益 / 归因 / 透视 / 分布里合并成一个聚合体
- **旧数据会不会跟着变**:**会** —— 同一段历史在开关开与关时呈现不同。
  所以必须让用户知道他打开的是**看法**而不是**数据**,并且**随时可关、关掉立刻恢复**
- **零差异基线**:开关关闭时,**所有页面必须与 v1.19.16 逐字一致**。
  基线取**已发布 tag `v1.19.16`**(不是当前工作区),否则分不清代码差异与数据漂移
- **调用方清单**:收益 / 归因 / 透视 / 分布四条路径靠人列**必漏** → 落 grep 护栏,
  扫「所有按账户聚合的入口是否都过了同一个合并层」

### 顺带的待查项(不在本版 FR 内)

`pivot`(PivotEngine)与 `period_summary`(FactViewService)两条**代码上没有共用求和逻辑**的路径,
总资产会差 **0.01**,且**跟数据分布走**(历史上出现过 0.03 / 0.06)。它不是任何一次改动引入的。

复现 issue #17 时它被再次触发,**刻意没有还原测试数据把它压绿** —— 那等于把真实的口径不一致藏起来。
分组 B 会大量动聚合路径,**是顺手把它收口的合适时机**,但先不进 FR,等 TDD 判影响面。

## 9 · 失败模式(pre-mortem)

**① 分组 B 的合并漏掉某条聚合路径 —— 而且不报错。**
四条路径(收益 / 归因 / 透视 / 分布)只改了三条,第四条仍按账户展开。
表现是「同一个页面上两块数对不上」,或者更糟:**看起来完全正常,只是某一块没合并**。
**怎么发现**:grep 护栏扫「所有按账户聚合的入口是否都过了同一个合并层」;
开关关闭态与 tag `v1.19.16` 的逐字比对。

**② 分组 A 的提示在不该出现的时候出现,变成噪声。**
比如每改一笔收入都弹一次,用户三天后开始无视它 —— 那这一版就白做了。
**怎么发现**:提示的触发条件必须**窄到可枚举**(该账户本期已有校准记录 + 本次改动会改变余额),
并把这个条件写成 e2e 断言的正反两面(该出现的出现、不该出现的不出现)。

**③ 「哪些账户算活期」被默默改了,用户不知道。**
流动性分层是既有标签,别处也能改。改完之后合并范围变了,而收益数字跟着变,
**用户看到数字变化却找不到原因**。
**怎么发现**:开关旁常驻显示「当前会被合并的是这 N 个账户」,让它可见而不是可推断。

**④ 护栏又绑在偶然事实上。**
本项目已经犯过四次(`v08-NAV-1` 绑单个路径、`v181-FLOAT-DOCK` / `v1617-FIVE` 绑三按钮数组、
`v11911` 数「出现两次」把收口误判成退化)。分组 B 的护栏最容易犯 ——
比如写死「合并后应该是 4 个账户」。
**怎么发现**:判据必须守**设计意图**(所有聚合入口共用同一个合并层),不守当下的数量或写法。

## 11 · 回滚与关闭

- **关开关够不够**:分组 B **够** —— 它是纯展示层,关掉立刻回到 v1.19.16 的样子。
  分组 A / C 无开关,但它们**只增加解释**,不改变任何既有数字,回滚风险接近零。
- **DB 迁移**:预计**无**。分组 B 的开关写进既有 `family_runtime_config`(KV 表,只加行)。
  若 TDD 阶段发现必须加表,则该迁移必须**可回滚**,并在这里补写。
- **不可逆动作**:**无**。本版不发送任何对外请求、不在第三方侧创建或删除任何东西、不重写历史数据。
- **prod 回滚路径**:`deploy/rollback.sh` + `app.jar.prev`(24 小时保留窗口)。
