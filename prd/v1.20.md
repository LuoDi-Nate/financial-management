## 0 · 这一版在解决什么

三条诉求看起来不相干,底下是同一件事:**系统自己知道、但没告诉用户的东西**。

- 你上个月确认过的余额,被这个月的一次收入改动悄悄改掉了 —— 系统知道,没说。
- 你有十几个活期账户,它们之间的划转对"家里有多少钱"毫无意义 —— 系统知道,但还是逼你按账户看。
- 归因这块在回答一个很有价值的问题,但页面没告诉你它在回答什么 —— 于是它等于不存在。

### 0.1 提交者的原话(第 1 条)

> 「一旦后期二次修改收入,错过或者影响了这个先后关系,或者没有重新去校验余额,就会导致**已经校准的余额失效**!……
> 我觉得至少有个强烈的提醒……因为校验后的余额一般来说,实际上一旦录入一次就不会再变更了,
> 或者说是它的**稳定性比收入的录入要高**。」

**他这句判断是对的,而且实际情况比他描述的更重。** 在测试环境用真实浏览器照他的路径复现过
(重开上月 → 删一笔收入 → 重录一笔金额不同的 → 重新关账):

| 他以为 | 实际 |
|---|---|
| 已校准的余额「失效」 | **被直接改掉了**:期末余额合计跟着那笔收入同步变化,页面零提示 |
| 仪表盘数字没更新 | **更新了** —— 没更新的是 AI 复盘那段解读(已在 v1.19.16 修掉) |

复现还额外坐实了一个**他没提、但一定会让人困惑**的条件:

> **当月还没填余额的账户,它上面的变动不会进「本期净资产变化」。**
> 复现时删掉的那 1,000 落在一个当月未填余额的账户上(19 个账户填了 18 个),
> 于是这 1,000 对仪表盘毫无影响。**「改了数据但数字不动」确实会发生**,而页面没有解释这个条件。

### 0.2 提交者的原话(第 2 条)

> 「由于这些划转相对频繁且多,所以不可能或者说不方便在账户金额校验的时候,把这些所有的划转全部有效地输入进去,
> 这就类似于支出的流水账的录入了,我觉得这是很难甚至是不可行的。所以我建议,
> 是否可以将所有活期账户在**录入时仍然按账户录入,但在最终统计收益、计算等场景下汇总展示**。
> 这实际上跟把当前已有的设计——所有支出都仅记录到一个总额在一定程度上是一个道理。」

**这个类比是准的。** 它和「支出只记一个总额」同源:
**不让录入负担跟着账户数量线性增长**,而这正是本项目「每月 10 分钟」硬约束的核心手段。

### 0.3 提交者的原话(第 4 条)

> 「最后就是那个什么归因,可能受限于投入时间和学习时间的原因,这个归因确实没搞明白怎么修改或者怎么玩。
> 反正看着显示没有录入,也不知道怎么改,能否简化/新增入口或加点什么指导之类的?」

一个需要看文档才会用的功能,等于没做。

## 1 · FR

### 分组 A · 别让一次改动悄悄推翻上一次的确认

| # | 要求 |
|---|---|
| FR-450 | 在**当月已校准过余额**的账户上新增 / 删除 / 修改收支时,**当场**告诉用户:这个账户的余额是什么时候校准的、这笔改动会把它从多少改成多少 |
| FR-451 | 提示里要给**下一步**,不是只给警告 —— 至少「知道了,余额按新值走」和「去重新校准这个账户」两条路 |
| FR-452 | 账户在填报页上要能**一眼看出**「本月余额校准过没有 / 什么时候校准的」,不用点进去 |
| FR-453 | **当月未填余额的账户,其变动不进「本期净资产变化」** —— 这个条件必须写在页面上。当用户改的恰好是这类账户时,要主动说明「这笔改动不会反映到本期净资产变化,因为该账户本月还没填余额」 |
| FR-454 | 重新打开已关账月份时,提示要列出**会被重算的东西**(而不是只说「会重算之后所有指标」),让人知道自己在动什么 |

**FR-450 的边界**:提示是**信息**不是**拦截**。用户按下去就该过,不设二次确认弹窗 ——
这个 app 的用户是家里人,不是审批流。

### 分组 B · 活期账户可以合起来看(可选 · 默认关)

| # | 要求 |
|---|---|
| FR-460 | 提供开关「把活期账户合并统计」,**默认关闭**。不开的用户,页面上一个像素都不变 |
| FR-461 | **录入侧完全不变** —— 仍然按账户填余额、记收支。合并只发生在统计与展示这一侧 |
| FR-462 | 开启后,被判定为「随时可取」的账户在**收益计算 / 归因 / 透视 / 分布**里合并成一个聚合体;账户之间的划转因此自然不再产生噪声 |
| FR-463 | 「哪些账户算活期」必须**用户可见、可改**,不能是系统猜的。复用现有的流动性分层,不新造一套概念 |
| FR-464 | 合并是**纯展示层**:底层数据一行不动,随时可关,关掉立刻恢复到今天的样子 |
| FR-465 | 页面要说清**代价**:合并之后,这几个账户之间的收益差异、单账户归因就看不到了 |

**为什么必须可选**(维护者定):收益、归因、透视今天全部锚在账户级。
把它改成默认行为,等于替所有现存用户改掉了他们已经看惯的口径 —— 那是不能替人做的决定。

### 分组 C · 归因要能自己看懂

| # | 要求 |
|---|---|
| FR-470 | 归因区**空态**要说清三件事:它在回答什么问题、为什么现在是空的、下一步做什么。不能只显示「没有录入」 |
| FR-471 | 用一句话解释归因在回答的问题(「这个月钱变了多少,分别是哪些账户/资产造成的」),就放在功能旁边,不放文档里 |
| FR-472 | 入口要在用户会经过的路径上,而不是要找 |

## 2 · 不做什么

- **不做自定义支出分类 / 支出报表** —— 拆到 [#18](https://github.com/LuoDi-Nate/financial-management/issues/18),单独设计
- **不改默认口径** —— 分组 B 全部行为都在开关后面
- **不加二次确认弹窗** —— 分组 A 是提示,不是审批
- **不做账户间划转的逐笔录入** —— 那正是提交者说「不可行」的东西,也是本项目的「刻意不做」

## 3 · 顺带记一个待查项(不在本版 FR 内)

`pivot`(PivotEngine)与 `period_summary`(FactViewService)两条**代码上没有共用求和逻辑**的路径,
总资产会差 **0.01**,而且**跟数据分布走**(历史上也出现过 0.03 / 0.06)。
它不是任何一次改动引入的,是两处四舍五入的时机/精度没有收口。

复现 issue #17 时它被再次触发,**刻意没有还原测试数据把它压绿** —— 那等于把一个真实的口径不一致藏起来。
本版做分组 B 时会大量动聚合路径,**是顺手把它收口的合适时机**,但先不写进 FR,等 TDD 阶段判断影响面。

## 4 · 验收标准

| # | 标准 |
|---|---|
| 1 | 在一个当月已校准余额的账户上删一笔收入,**当场**看到提示,且提示里有该账户校准时间与前后余额 |
| 2 | 提示不阻断操作:点「知道了」之后改动照常生效 |
| 3 | 在一个当月**未填余额**的账户上改收支,页面明确告诉你这笔改动不进本期净资产变化 |
| 4 | 关掉分组 B 的开关时,所有页面与 v1.19.16 **逐字一致**(护栏级校验,不靠肉眼) |

| 6 | 分组 B 开→关→开,数据不发生任何变化(纯展示层) |
| 7 | 归因区在空态下,一个没读过文档的人能说出「它在回答什么」和「我下一步该做什么」 |
| 8 | PC + 移动双端截图核对排版 |
