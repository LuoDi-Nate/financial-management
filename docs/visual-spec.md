# 家庭账房 · 视觉设计规范(UED 提案)

> 这份文档回答的是"**应该是什么**",不是"现在是什么"。
> 每条规范都从产品约束和主题推导,并给出可判定的数值 —— 能用来驳回一个 PR,才算规范。
> 与现状的差距集中在末尾附表,正文不掺。

---

# 0 · 立场:规范从哪来

## 0.1 三个硬约束

这三条不是偏好,是产品事实,决定了后面所有取舍。

**约束一:每月 10 分钟,低频**

用户一个月来一次。这意味着**每次访问都是"半个陌生人"** —— 上次点哪个按钮、那个图标什么意思、这个数字什么口径,全都忘了。

> 推论:**零学习成本是硬要求,不是加分项。** 任何需要"用过一次才懂"的设计都不合格。图标必须配文字;颜色必须可解释;口径必须能当场查到。

**约束二:两类能力差异极大的用户共用一套界面**

一个是工程师(会看图表、能理解"穿透""笛卡尔积"),一个是非技术家庭成员。

> 推论:**规范服务下限,不服务上限。** 可读性、可点性、文案的判据都取"非技术用户在手机上能不能用",而不是"信息密度够不够专业"。高级信息可以存在,但必须是渐进披露,不能挡在主路径上。

**约束三:金额既要看清,又要随时能藏**

家里、地铁上、给人看屏幕。

> 推论:金额是**一等公民**,排印上必须最优待遇;同时隐私态是**全局模式**而不是某页的开关,视觉上必须让用户随时知道"我现在是藏着的"。

## 0.2 主题解读:「起居室里的银行家账册」给我们什么

这个主题选得对,因为它一次性解决了本产品最难的两件事:

| 产品难题 | 账册主题如何解决 |
|---|---|
| 财务数据天生冰冷,但这是"家庭"产品 | **温度来自纸,不来自色彩。** 米色纸底 + 纹理给出温度,同时不需要用鲜艳颜色讨好用户 —— 那会削弱财务的严肃性 |
| 数字凭什么可信 | **可信来自秩序。** 手写账册的权威感来自规整的行列、对齐的数字、留痕的修改,不来自任何视觉特效 |
| 功能越加越多,如何不乱 | **账册天生克制。** 没有装饰的余地,新元素必须回答"账册上有这个东西吗" |

**主题的边界 —— 三处必须破例:**

账册是纸上的只读记录,而我们是屏幕上要输入的工具。下面三处如果死守主题,会害事:

1. **对比度**:纸的低对比在反光的纸上成立,在发光屏幕上不成立。**可读性优先于纸感。**
2. **可操作性**:账册没有按钮。输入控件必须有明确的"可操作"信号,不能为了纸感做成一片平的。
3. **警示**:账册不会喊。但错误和不可逆操作必须喊。**安全优先于克制。**

这三条是"主题让位"的唯一合法理由。其余情况一律以主题为准。

## 0.3 五条设计原则(review 时直接引用)

| # | 原则 | 判定方法 |
|---|---|---|
| P1 | **看得清优先于好看** | 任何承载信息的文字,对比度 ≥ 4.5:1;中文字号 ≥ 12px |
| P2 | **一个颜色一个意思** | 任一颜色只能属于一条色轴(见 §1.1);跨轴使用即不合格 |
| P3 | **点得中优先于装得多** | 移动端可点区域 ≥ 44×44px;行内并列操作 ≤ 3 个 |
| P4 | **秩序表达可信,不靠特效** | 数字必须等宽对齐;不用阴影/渐变/发光表达重要性 |
| P5 | **自解释优先于简洁** | 图标必须配文字或 aria-label;数字必须能查到口径;状态必须写明下一步 |

冲突时的优先级:**P1 > P3 > P5 > P2 > P4**。即可读 > 可点 > 可懂 > 一致 > 美观。

# 1 · 色彩:按"轴"分配,不按"好看"分配

## 1.1 四条色轴(这是整套配色的核心)

色彩失控的根源永远是**一个颜色承担多个含义**。规范先划轴,再分色。**同一颜色不得跨轴使用。**

| 轴 | 管什么 | 分配的色 | 出现频率 |
|---|---|---|---|
| **中性轴** | 纸、墨、线 —— 承载 95% 的界面 | paper / card / ink 三阶 / rule | 极高 |
| **交互轴** | 可点、当前、焦点 —— 只表达"你能操作这里" | **brass 系,独占** | 中 |
| **数据轴** | 数值的正负、盈亏 —— 只表达"这个数是什么性质" | forest(正)/ rust(负) | 中 |
| **警示轴** | 错误、不可逆、逾期 —— 只表达"你要小心" | rust + **必须带边框或填充**(见 §1.4) | 低 |
| **分类轴** | 账户类型、行业、成员 —— 只表达"这属于哪一类" | 低饱和中性色板,**禁用上面任何语义色** | 中 |

三条最重要的禁令:

- **brass 不得表达数据。** 一个数字染成铜金色,用户无法判断是"这个数很重要"还是"这里能点"。
- **forest / rust 不得表达可点。** 绿色按钮会被读成"这是正向的数据"。
- **分类色不得借用 forest / rust / brass。** 否则"绿色的理财类型"会被误读为"这类是赚的"。

> 现状里 `WEALTH → forest` / `STOCK → brass` / `LOAN → rust` 正是这条禁令要否掉的:理财账户是不是绿色跟它赚不赚钱无关,但用户会连起来。分类应当靠 §1.5 的方案表达。

## 1.2 中性轴:三阶纸 + 三阶墨,以及必须守住的对比度

这是全套规范里**唯一不许打折**的部分。以下比值为实测(WCAG 2.1,底色分别为 `card #FFFCF5` 和 `paper #F4EFE6`)。

**纸(底)**
```
--paper       #F4EFE6   页面底
--paper-soft  #EDE6D7   区块底 / 输入框底
--paper-deep  #E5DCC8   凹陷 / 进度槽 / 硬投影
--card        #FFFCF5   内容卡底
--card-soft   #FAF4E6   次级卡底 / 行 hover
```

**墨(字)—— 三阶各有准入范围**

| token | 值 | on card | on paper | 允许承载 |
|---|---|---|---|---|
| `--ink` | `#1A1714` | 17.4:1 | 15.6:1 | 数据本体、标题、正文 |
| `--ink-soft` | `#5C5147` | 7.5:1 | 6.7:1 | 说明文字、次要标签 |
| `--ink-subtle` | **`#706657`** | 5.5:1 | 4.9:1 | 元信息(时间/序号/口径/计数) |
| `--ink-faint` | `#A09486` | 2.9:1 | 2.6:1 | **仅装饰**:水印、禁用态、占位图形 |

**这里有一处必须改**:元信息色若取 `#A09486`,对比度只有 **2.9:1 / 2.6:1**,连大字号的 3:1 都不到。而元信息恰恰是字号最小(10-11px)的一层 —— 小字 + 低对比 = 双重不可读,对 40 岁以上的非技术用户基本等于隐形。

规范取值 `#706657`(5.5:1 / 4.9:1),双底过 AA。原来那个浅值降级为 `--ink-faint`,**只许画装饰,不许写信息**。

**线**
```
--rule       #BCAE96   常规分隔(on card 2.1:1 —— 非文字,不受 4.5 约束)
--rule-soft  #DBD0BC   行内弱分隔
--rule-ink   #1A1714   表头总账线 / 分节双线(账册的"重线")
```
分隔线不承载文字,不受 4.5:1 约束,但**必须 ≥ 1.8:1** 才在屏幕上确实可见。账册的层次很大程度靠线的粗细与深浅表达,这是主题的核心手段,不能省。

## 1.3 语义色:准入规则

| token | 值 | 可做文字? | 用途 |
|---|---|---|---|
| `--brass` | `#B08642` | **否**(3.2:1) | 底、边框、图表装饰、焦点环 |
| `--brass-text` | **`#85642F`** | 是(5.3:1 / 4.8:1) | 链接、eyebrow、可点强调文字 |
| `--forest` | `#4F6B47` | 是(5.8:1 / 5.2:1) | 正数、收入、完成 |
| `--rust` | `#9C4A2A` | 是(6.0:1 / 5.4:1) | 负数、支出;加边框后转为警示 |
| `--slate` | `#3C4A5A` | 是(8.8:1) | 中性强调(不表达好坏) |

**规范:`brass` 与 `brass-text` 必须分开两个 token。** 铜金色作为底色很好,作为小字文字只有 3.2:1,不合格。现状只有一个 brass + brass-deep,而 brass-deep 在 paper 底上是 4.34:1 —— 差一点点,不能用于 10px 元信息。分成两个 token 才能让规范可执行,而不是靠开发每次自己判断。

## 1.4 数据轴与警示轴:靠形态区分,不靠色相

难点:"支出 ¥5,000" 和 "删除此账户" 都想用红。若给警示另配一个红,账册上出现两种红 —— 违反主题的克制。

**规范:同色,不同形态。**

| | 视觉形态 | 含义 | 例 |
|---|---|---|---|
| 数据轴 | **纯文字**,无边无底 | 只是信息,不需要你做什么 | `-¥5,000`、`支出`、`本期欠款` |
| 警示轴 | **必须有边框或填充**,可配警示图标 | 需要你注意或做决定 | 危险按钮(rust 描边)、逾期 pill(rust 边+底)、错误块(rust 左脊) |

一句话判据:**有框 = 要你动作;无框 = 只是数字。**

这条规则的价值在于它可判定 —— 看一眼有没有边框就知道对不对,不需要辩论"这个红够不够红"。

## 1.5 分类轴:三种方案,按类别数量选

分类色最容易失控(类型 8 个、行业 49 个、成员 N 个)。按数量给三套方案:

**方案 A · ≤ 6 类(账户类型):中性底 + 左侧 3px 色条**

不整体染色,只在标签左缘加一道 3px 色条。理由:整体染色会与状态标签(§6.2)撞车,而色条既能区分又不抢注意力,且符合账册"骑缝标记"的意象。

色条取**低饱和中性色板**(与语义色明确区分):
```
--cat-1 #6B7A8F  蓝灰    --cat-2 #8A7B6B  棕灰
--cat-3 #7A8A72  橄榄灰  --cat-4 #8A7286  紫灰
--cat-5 #6F8384  青灰    --cat-6 #8F8360  黄灰
```
**分配必须查表且写进代码常量**,不许各页自选 —— 同一类型在两个页面显示不同色是最伤信任的细节。加新枚举值时同步这张表。

**方案 B · 7-50 类(行业):后台可配的莫兰迪双环板**

图表专用,主界面不出现。低饱和是必须的 —— 高饱和分类色在米色纸底上会显得刺眼且互相打架。

**方案 C · 成员(人):固定 5 色轮,首字圆头像**

人不是"分类"而是"身份",给独立色板,且**同一人全站永远同一色**(这条已经做对了,写进规范固化)。头像色需与白字有 ≥ 4.5:1 对比。

## 1.6 深色模式:明确不做

`theme-color` 与页面底色必须一致(取 `#F4EFE6`)。

理由:"账册"隐喻的核心载体是纸,纸是亮的。做深色模式等于重新定义整个隐喻(墨底纸字的账册不存在),收益远小于成本。**明确写进规范"不做",避免以后反复讨论。**

# 2 · 字体与数字排印

这是本主题最该发力的地方 —— 账册的美学就是数字排印的美学。

## 2.1 三套字体的职责边界

| 字体 | 职责 | 不许用在 |
|---|---|---|
| **Fraunces**(display serif) | 标题、KPI 数值、印章、页码水印 | 正文段落、表格内容 |
| **Source Serif 4**(正文 serif) | 段落、说明、空状态文案 | 数字、标签 |
| **JetBrains Mono** | **一切数字** + 标签/表头/时间/元信息/按钮文案 | 中文长句(超过 12 字改用正文体) |

**关键规范:所有数字一律 mono。** 不只是"金额",包括日期、期数、百分比、计数。理由:等宽数字在列表里纵向对齐,这是账册可信感的**唯一来源**。一处用比例字体的数字就会破坏整列对齐。

Mono 中文的限制:JetBrains Mono 无中文字形,会回落到系统字体,且 `letter-spacing` 会让中文显得松散。**mono 里的中文不超过 12 字**,长文案改用正文体。

## 2.2 字号阶梯:模数化,8 档封顶

散乱的字号是维护灾难的开始。规范定 8 档(1.25 模数,基准 15px),**不在表内的字号不许出现**。

| 档 | 值 | 用途 |
|---|---|---|
| `meta` | 10px | **仅 mono 大写英文/数字**(eyebrow、表头、版本号) |
| `xs` | 12px | 元信息中文、辅助说明 —— **中文红线** |
| `sm` | 13px | 表格内容、pill、次要正文 |
| `base` | 15px | 正文基准 |
| `lg` | 19px | 小标题、区块标题 |
| `xl` | 24px | 页面副标题、中号 KPI |
| `2xl` | 31px | KPI 主值 |
| `3xl` | 39px | 页面主标题、大数展示 |

**中文最小字号红线:12px。** 低于 12px 的中文在移动端(尤其非技术用户)不可读。10px 档**只允许 mono 大写英文和数字** —— `2026 · 05 · OPEN`、`v1.5.2`、`CASH` 这类可以,中文说明不行。

**所有字号必须走缩放变量**:`calc(Npx * var(--fs-scale,1))`。写死 px 的字号会让全局字号档位对它失效 —— 而字号档位正是为看不清小字的用户准备的,这个洞不能有。

## 2.3 金额排印规范(账册的灵魂)

金额是本产品的一等公民,单独立规。

**三段式视觉分层**:一个金额里,不是所有字符都同等重要。
```
¥  1,234,567 .89
↑      ↑       ↑
弱     强      弱
```
- **货币符号**:0.55em + `ink-subtle` + 上标对齐 —— 用户知道自己在看什么币种就够了,不需要它抢戏
- **整数部分**:全尺寸 + `ink` + `tabular-nums` —— 唯一的主角
- **小数部分**:0.75em + `ink-subtle` —— 家庭记账的决策不发生在"分"这一位

**硬性规则**:
1. `font-variant-numeric: tabular-nums` 无例外
2. 千分位必须有
3. 负数用 `-` 前缀 + `rust`,**且对齐时预留符号位**(正数也占一个符号宽度),否则整列会错开一位
4. **右对齐**,永远
5. 缩写(`¥304k`)只允许出现在**汇总带和图表轴**;详情、列表行、填报页必须给完整数字 —— 用户核对账目时看到 `¥304k` 是不可接受的
6. 隐私态:`blur(7px)` 且 `user-select:none`。**只遮绝对金额,不遮百分比与比值** —— 后者不敏感,遮了图表就失去意义

## 2.4 行高与字距

| 场景 | 行高 | 字距 |
|---|---|---|
| 正文段落 | 1.65 | 0 |
| 表格 / 列表行 | 1.45 | 0 |
| 数字 | 1.2 | `0.01em` |
| mono 标签(uppercase) | 1.3 | `0.12em` |
| 大标题 | 1.15 | `-0.01em` |

中文正文行高不低于 1.6 —— 中文字身满,行距不足会糊成一片。这比西文需要更多呼吸。

# 3 · 空间与密度

## 3.1 4px 刻度

所有间距取 4 的倍数,常用 8 的倍数:`4 / 8 / 12 / 16 / 24 / 32 / 48 / 64`。
不许出现 5 / 7 / 9 / 11 / 13 / 19 / 22 这类值 —— 它们的存在说明有人在"目测微调",而目测微调无法维护。

## 3.2 两端密度分档(这是两端最本质的差别)

PC 和移动的密度不是"一个大一个小",而是**优化目标不同**:

| | PC(≥768px) | 移动(<768px) |
|---|---|---|
| 优化目标 | **信息密度** —— 一屏看到更多、便于横向对比 | **可点性** —— 手指点得中、单手可达 |
| 表格/列表行高 | 44px | 56px |
| 卡片内边距 | 24px | 16px |
| 区块间距 | 32px | 24px |
| 同组元素间距 | 12px | 8px |
| 并列操作数 | ≤ 3(超出收进 `⋯`) | ≤ 2(超出收进底部操作面板) |

注意移动端是**行更高但内边距更小** —— padding 让位给触摸高度。这不矛盾:小屏上留白是奢侈品,可点性是必需品。

## 3.3 触摸目标底线(不可协商)

| 元素 | 最小可点尺寸 |
|---|---|
| 移动端一切可点元素 | **44 × 44px** |
| PC 可点元素 | 32 × 32px |
| 相邻可点元素间距 | ≥ 8px |

**允许"视觉小、热区大"**:小图标(如口径 `?`)可以视觉 14px,但必须用不占布局的伪元素扩热区:
```css
.tap { position: relative; }
.tap::after { content:''; position:absolute; inset:-12px; }
```
这是唯一被允许的"看起来小于 44px"的情况。

## 3.4 容器与栅格

- 最大内容宽度 `1400px`,页边距 PC `40px` / 移动 `16px`
- 12 栅格,`gap 24px`(PC)/ `16px`(移动)
- **正文单列宽度上限 72 字符** —— 超过会显著降低阅读效率

# 4 · 形状与层次:纸世界里怎么表达 z 轴

主题禁用了 Material 那套模糊阴影(那是塑料和玻璃的语言,不是纸)。那层级靠什么?

## 4.1 四级"升起",按顺序使用

| 级 | 手段 | 用在 |
|---|---|---|
| L0 同平面 | `1px solid var(--rule)` 分隔 | 默认。列表行、区块之间 |
| L1 微升 | **底色变化**(`card` → `card-soft`),不加边不加影 | 行 hover、次级区块、表格分组头 |
| L2 升起 | `1px solid var(--ink)` + `4px 4px 0 var(--paper-deep)` **硬位移投影** | 重要卡片、弹层。硬投影 = 纸叠纸的真实投影 |
| L3 浮层 | `scrim rgba(26,23,20,.4)` + `backdrop-blur(2px)` + L2 卡片 | 模态、底部 sheet |

**禁令:不许用模糊阴影表达层级。** `box-shadow: 0 4px 12px rgba(...)` 这类写法在本主题里一律不合格 —— 纸不会发光也不会悬浮。唯一例外是浮动按钮(FAB)和 toast,它们确实"浮"在纸面之上,允许一层极淡的柔影。

## 4.2 圆角:三个值,不许有第四个

| 值 | 用在 | 为什么 |
|---|---|---|
| `0` | 按钮、输入框、表格、卡片 | 纸的裁切边是直的 |
| `1px` | pill / 标签 | 唯一带圆角的组件族,借此与按钮区分 |
| `999px` | 头像、浮钮 | 圆形物件(印章、纽扣) |

例外:底部 sheet 顶部 `16px`(移动交互惯例,用户预期它能拖),FAB `50%`。

**圆角是本主题的识别符。** 一旦出现 8px 圆角卡片,整个"账册"就塌成了普通 SaaS。这条要严守。

## 4.3 边框:层次由粗细与深浅表达

| 写法 | 语义 |
|---|---|
| `0.5px rule-soft` | 最弱分隔(行内) |
| `1px rule` | 常规分隔 |
| `1px ink` | 重要边界(L2 卡片、表头下线) |
| `2px ink` | 强调区块(如填报第一步) |
| `3px double rule` | 小节收尾 |
| `4px double ink` | 大节收尾(最后一步) |
| `3-4px 左脊`(语义色) | 提示条 / 错误块 —— 左侧色脊是本主题的标准提示形态 |

# 5 · 动效:纸的物理性

纸的物理特性:**轻、有阻尼、不弹跳、不发光**。所有动效必须符合这个物理直觉。

| 场景 | 时长 | 曲线 | 位移 |
|---|---|---|---|
| 颜色/边框过渡 | 150ms | `ease` | — |
| 按钮按下 | 即时 | — | `translateY(1px)` |
| 元素入场 | 400ms | `cubic-bezier(.2,.8,.2,1)` | 上移 6px + 淡入 |
| 抽屉/sheet | 260ms | `cubic-bezier(.22,1,.36,1)` | — |
| 浮层淡出 | 200ms | `ease-out` | — |
| 阶梯揭示 | 每级 +80ms | 同入场 | 最多 4 级 |

**禁令**:
- **不许 bounce / elastic / spring 曲线** —— 那是橡胶,不是纸
- **位移不超过 8px** —— 纸不会飞
- **不许旋转/缩放整个卡片** —— 纸不会自己转
- 加载动画只允许:线性进度条、旋转 loader 图标(功能性)、印章绘制(品牌时刻,**只在首次会话**)

**减少动态偏好必须尊重**:
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration:.01ms !important; animation-iteration-count:1 !important;
    transition-duration:.01ms !important; }
}
```
功能性 loader 可保留。这不是加分项 —— 有前庭障碍的用户会因为动画产生生理不适。

# 6 · 组件规范

## 6.1 按钮

**账册上没有按钮**,所以按钮的隐喻是"盖章"(主操作)和"贴标签"(次操作)。这决定了它的形态:方正、墨色、按下有下沉。

### 变体:五个,按"用户损失"分级

分级依据不是重要性,而是**点错的代价**:

| 变体 | 形态 | 用在 | 单页上限 |
|---|---|---|---|
| `primary` | 墨底纸字 | 本区块用户最该点的那一个 | **每区块 1 个** |
| `secondary` | 透明 + 1px 墨边 | 并列的、地位相当的操作 | 不限 |
| `tertiary` | 无边无底,hover 才出边 | 列表行内的密集轻操作 | 行内 ≤ 3 |
| `accent` | 铜底纸字 | 新功能 / AI 入口(引导性) | 全站 ≤ 3 处 |
| `danger` | 透明 + 1px rust 边 + rust 字 | **不可逆**:删除、归档、强制关账 | 每页 ≤ 1 显式 |

**`danger` 用描边而非实心红。** 实心红会成为页面最醒目的元素,而"删除"永远不该是视觉焦点 —— 它只需要在用户已经找到它时警示到位。hover 时填充实心,给出最后一次强提示。

**判据:代价不可逆 → danger;区块内首要 → primary;其余按密度选 secondary/tertiary。** 与"这个功能重不重要"无关。

### 尺寸:三档,语义绑定

| 档 | 高度 | 字号 | 用在 |
|---|---|---|---|
| `sm` | 32px(移动 **40px**) | 12px | 列表行内 |
| `md` | 40px(移动 44px) | 12px | 常规表单、页头 |
| `lg` | 48px | 13px | 页面唯一重点操作 |

移动端 `sm` 档不得低于 40px,且必须配 `.tap` 扩到 44px。

### 六个状态,一个都不能少

| 状态 | 规格 | 为什么必须有 |
|---|---|---|
| default | 见变体表 | — |
| `:hover` | 加深 / 反白 / 出边 | PC 的可点提示 |
| `:active` | `translateY(1px)` | **移动端没有 hover,这是唯一的按下反馈** |
| `:focus-visible` | `outline: 2px solid var(--brass); outline-offset: 2px` | 键盘用户唯一的定位手段 |
| `[disabled]` | `opacity:.45; cursor:not-allowed; pointer-events:none` | 请求中的按钮必须看起来不可点,否则用户重复提交 |
| loading | 文字保留 + 尾部旋转 loader + 自动 disabled | 不许把文字换成"加载中"(布局跳动) |

`:active` 和 `[disabled]` 是最容易漏、后果最实际的两个:前者让移动端点击"没有反应",后者让用户在慢网络下重复下单。

### 图标与文案

- 图标一律 inline SVG,`stroke="currentColor"` —— 自动继承所有状态的文字色,不必为图标单独写状态
- 尺寸:sm 配 12px,md 配 14px,lg 配 16px;间距 `gap: 8px`
- 位置:左侧 = 动作类型;右侧 = 方向/流转
- **禁止纯图标按钮**(除全站公认符号:关闭 ×、汉堡)。低频使用意味着用户认不出图标 —— 这是约束一的直接推论
- 必须带 `aria-hidden="true"`(文字已表意)
- 文案带后果:不写"提交"写"我已记账完毕";不写"确定"写"保持上月";danger 必须含动词+对象("归档此账户"而非"归档")
- 预期 > 3s 的操作,按钮旁标时长(`+15s`)

### 排列

- 次操作在左,主操作在右;移动端竖排时主操作在上
- 并列不超过 3 个,超出收进 `⋯`;移动端超出 2 个收进底部操作面板
- **不许在圆角、字距、大小写上做变体** —— 那些属于统一层

## 6.2 标签

标签在账册上的对应物是**骑缝标记和贴纸**。它的规范难点不在样式,在**先分清它有四种完全不同的角色**。

### 四类标签(必须视觉可区分)

| 类 | 回答什么 | 可点 | 形态规范 |
|---|---|---|---|
| **分类** Category | 这条数据"是什么" | 否 | 中性底 + **左侧 3px 分类色条** + `ink-soft` 字 |
| **状态** Status | 这条数据"怎么了" | 否 | **整体染色**(语义色底+边+字) |
| **筛选** Filter | 我"要看什么" | **是** | 未选:中性底 + hover 变 brass 边;已选:墨底反白 |
| **计数** Count | 有多少个 | 否 | **不套标签样式**,纯 `mono + ink-subtle` |

这套区分的价值:**用形态而非颜色区分角色**。分类用左色条、状态用整体染色、筛选靠 hover 反馈、计数干脆不做成标签 —— 用户扫一眼就知道哪个能点、哪个是分类、哪个是状态,不需要记颜色含义。

**最容易犯的错**:让筛选标签和分类标签长一样。用户不知道哪个能点,只能挨个试 —— 对一个月来一次的用户,这是纯粹的挫败。

### 状态标签的语义色映射

| 状态性质 | 色 | 例 |
|---|---|---|
| 完成 / 正向 | forest | 已入账、我已填 |
| 缺失 / 逾期 / 异常 | rust + 边框(警示轴) | 我未填、已过截止 |
| 进行中 / 当前 | brass | 账期 OPEN |
| 中性 / 未启用 / 无数据 | 透明底 + `rule-soft` 边 + `ink-subtle` 字 | 本期未填、未穿透 |

"无数据"必须有专门的弱化态 —— 用默认样式会让"没数据"看起来像一个正常状态。

### 尺寸:两档

| 档 | 字号 | padding | 用在 |
|---|---|---|---|
| `sm`(默认) | 12px | 4px 10px | 列表行、筛选器、状态 |
| `md` | 13px | 6px 12px | 页头账期、KPI 旁 |

**不设 9px / 10px 档。** 中文低于 12px 不可读(§2.2 红线)。若空间不够放 12px 标签,说明该处不该用标签 —— 改用图标或纯文字。这是"看得清优先于装得多"的直接应用。

### 共性

- 字体 mono,字距 `0.1em`,圆角 `1px`,边框恒 1px(即便同色)
- `inline-flex; gap: 6px`,可嵌 12px SVG
- 单行原子,**不许换行、不许放两行内容** —— 多行内容用卡片
- 长文案 `whitespace-nowrap`,由容器负责 `flex-wrap`

## 6.3 表单

账册是**要填写的**,这是主题与产品最贴合的地方,应该充分利用。

### 两种输入形态,按任务性质分

这不是"随便选一个",而是有明确判据:

| 形态 | 视觉 | 用在 | 为什么 |
|---|---|---|---|
| **登记式** | 下划线(focus 变 2px brass 底线) | 一次性设置:账户信息、成员、汇率、配置 | 对应账册的横线填写栏,轻、像在纸上写 |
| **操作式** | 方框(1px rule + `paper-soft` 底) | 反复输入:金额、搜索、筛选 | 需要明确的边界感和点击目标,`h-36/40px` |

判据:**这个字段是"登记一次"还是"每月要动"?** 前者用下划线,后者用方框。填报页全是方框,设置页全是下划线。

### 标签(label)

单一来源,不许手写重复样式:
```
mono / 12px / letter-spacing .12em / uppercase / ink-subtle / margin-bottom 6px
```
必填标记:标签后 `*`(rust)。不用"(必填)"文字 —— 占宽且重复。

### 数字输入

- 一律 `tabular-nums` + **右对齐** + mono
- 移动端 `font-size ≥ 16px`(**低于 16px 会触发 iOS 聚焦时整页缩放**,这是硬约束不是偏好)
- `inputmode="decimal"` 唤起数字键盘
- 聚焦时全选(`onfocus="this.select()"`)—— 月度填报是"覆写上月值"而非"追加",全选省掉一次删除
- 配行内清空按钮,`tabindex="-1"` 不进 Tab 序
- 参考值(上期末)放输入框**下方作为独立说明**,不作为 placeholder 或预填值 —— 预填会让用户误以为"已经填了"

### 校验与错误

**三层,缺一不可**:

1. **输入时**:格式限制(`type`/`step`/`min`/`max`),但不在用户打字过程中报错
2. **失焦时**:字段级错误 —— 输入框 `border-rust` + 下方 12px rust 文案
3. **提交后**:表单顶部汇总块(rust 左脊 + rust 底 5%),列出所有错误并锚点跳到首个错误字段

**错误必须留在页面上,不能只用 toast。** toast 4 秒消失,而用户回头改字段时正需要看到错在哪 —— 这是 toast 的结构性缺陷,不是文案问题。

错误文案规范:**说清怎么改,而不是说什么错了。**
- 不合格:"金额格式不正确"
- 合格:"金额请填数字,最多两位小数(如 1234.56)"

## 6.4 列表与表格

账册的核心形态。**这里的规范优先级最高**,因为用户 80% 时间在看列表。

### 表格(PC)

| 元素 | 规范 |
|---|---|
| 表头 | mono 10px uppercase,字距 `.16em`,`ink-subtle` 字,**下边 1px `ink`**(总账线,非灰线) |
| 行分隔 | `1px rule-soft`,比表头线弱 |
| 行高 | 44px(内容 padding 12px 14px) |
| 数值列 | 右对齐 + mono + tabular-nums |
| 文本列 | 左对齐 |
| 行 hover | 底色 `card-soft`,不加边不位移 |
| **禁止斑马纹** | 账册用细线不用色块;斑马纹会与"行 hover"和"分组底色"三者打架 |
| 排序 | 列头可点 + `aria-sort` 三态,指示器用 CSS 三角(不用字形) |
| 分组 | 整行 `card-soft` + `border-t 2px`,组头含头像/名称/计数 |

### 卡片(移动)

表格在窄屏不可用 —— 但**不是"横向滚动的表格",而是重新组织信息**:

```
[头像] 名称(可点,最强)          [类型标签]
       元信息:序号 · 主理人
       [分类标签] [风险标签]
       ─────────────────────────
       本期末                 ¥73,200   ← 最大最强
       ─────────────────────────
       [主操作] [次操作]  [⋯]
```

规范:
- **一张卡一个主体**,不许把两条数据塞一张卡
- 层级:名称(可点)> 金额 > 标签 > 元信息 > 操作
- 金额右对齐且是卡内最大字号 —— 用户扫列表就是在扫金额
- 操作 ≤ 2 个显式,其余收进 `⋯`

### 表格与卡片必须同源

两端渲染同一份数据,操作集合必须完全一致。**共用的行内操作抽成单一 fragment,两端传尺寸参数复用。** 各写一套必然漂移 —— 加了一个操作只改一边,编译器抓不到。

### 分组与排序的默认

- **默认按人分组**(不是按类型、不是按金额)。产品是家庭协作,第一个问题永远是"这是谁的账"
- 组内默认按显示顺序,其次按金额降序
- 排序状态必须进 URL(可分享、可后退)

### 空状态:三段结构

```
[状态]   这里还没有 X
[原因]   因为 Y 还没做
[动作]   [去做 Y →]   ← 可点,直达
```
**不许只写"暂无数据"。** 对一个月来一次的用户,空状态是他唯一的求助信号。

容器:虚线框(`1px dashed rule`)+ `card-soft` 底 + 居中,padding 32px。

### 加载与骨架

- 首屏:骨架屏(纸色块,不用旋转 loader)
- 局部刷新:目标区域 `opacity .5` + 顶部进度条
- 追加加载:底部 loader
- **禁止整页遮罩 loading**(会丢失用户的滚动位置和填报现场)

## 6.5 翻页:三种策略,按数据性质选

这条现状没有统一规则,必须定下来,否则每次数据量涨上来就临时打补丁。

| 数据性质 | 策略 | 判据 |
|---|---|---|
| **有界集合**(账户、成员、目标)| **不分页,全量渲染** + 分组 + 锚点导航 | 上限可预期(家庭 < 50) |
| **单调增长的时间序列**(账期、流水、日志)| **默认显示最近 N 期 + "加载更早"** | 每月必增,无上限 |
| **管理后台的审计类**(通知日志、备份记录)| **传统页码分页** | 需要精确定位第几页 |

时间序列**必须**从第一天就按第二种做,不能等长了再改 —— 那时用户的数据已经在受影响。

分页组件规范:
- 位置感:`共 88 期 · 第 1 / 4 页(每页 24)`
- **方向带语义**:`← 上一页(更新)` / `下一页(更旧) →` —— 时间序列里"上一页"是更新还是更旧,不标注一半用户会猜错
- 禁用态用 `<span>` 而非 `<a>`,`opacity .4` + `cursor:not-allowed`
- 状态进 URL

## 6.6 反馈:账册式"留痕"

账册的反馈方式不是弹窗,是**在纸上留下痕迹**。这个隐喻能带来比 toast 更好的反馈设计。

### 四层反馈,按"用户是否需要知道"分

| 层 | 手段 | 用在 |
|---|---|---|
| **痕迹**(推荐) | 数据行本身变化 + 短暂高亮(brass 底 600ms 淡出) | 保存成功、金额更新 —— **数据变了就是最好的反馈** |
| **行内** | 按钮上的 loader + disabled | 请求进行中 |
| **消息** | toast,顶部居中,4s | 与当前视图无关的结果(后台任务完成) |
| **阻断** | 模态 | 不可逆操作确认 |

**优先用"痕迹"而不是 toast。** 保存了余额,行上的数字变了、"待填"变"已填"、勾变绿 —— 用户已经知道成功了,再弹一个"保存成功"是噪音。toast 应该留给"结果不在当前视图里"的情况。

### 确认对话:必须用产品自己的弹层

不许用原生 `confirm()`。原生弹窗是系统样式(无纸底、无 mono、移动端带域名前缀),且 `\n\n` 是唯一排版手段,写不出层次。

确认弹层的**三段结构**:
```
标题:   要做什么(动词+对象)
正文:   会发生什么 / 影响哪些数据
脚注:   能否撤销
按钮:   [取消(secondary)]  [确认(danger)]
```
不可逆操作的确认按钮**必须是 danger 变体**,且文案重复动作("确认归档"而非"确定")。

### 错误提示分级

| 情况 | 处理 |
|---|---|
| 字段级 | 输入框红边 + 下方文案,留在页面 |
| 表单级 | 顶部汇总块 + 锚点跳到首个错误 |
| 登录过期(401) | 直接跳登录,带回跳地址 |
| 权限/CSRF(403) | toast 提示刷新 |
| 服务端错误(5xx) | **toast + 留在当前页,绝不跳错误页** |

最后一条是硬规范:填报页填了一半遇到 5xx,跳错误页等于数据全丢。**任何情况下不得因为错误而丢失用户已输入的内容。**

## 6.7 数据可视化

### 铁律

1. **数值直接标在图形上**(扇片/柱顶/数据点),hover tooltip 不算 —— 用户不会为了看数字去悬停,移动端更没有 hover
2. **分类色用低饱和板**,禁用语义色(§1.1)
3. **不用渐变填充、不用发光、不用 3D** —— 纸上的手绘统计图
4. 网格线极弱(`rgba(58,48,42,.06)`),轴线 `rule`
5. 图表字号跟随全局字号档位(canvas 够不到 CSS,需 JS 换算重绘)
6. 隐私态:标签重算(遮金额)但**形状不变** —— 图形本身不敏感

### 图表选型判据

| 要回答的问题 | 图型 |
|---|---|
| 构成占比(≤7 类) | 环图 + 直接标注 |
| 构成占比(多层级) | 旭日图 |
| 随时间变化 | 折线(连续)/ 柱状(离散期间) |
| 两个维度交叉 | 交叉表 + 热力底色 |
| 对比正负 | 双向水平柱(零轴居中) |

**类目 > 7 个不用饼图/环图** —— 人眼无法比较相近扇形角度。改横向条形图。

### 移动端图表

不是缩小,而是**降级信息量**:字号降 2px、图例改横排滚动、x 轴标签旋转或抽稀、padding 收紧、必要时减少显示的系列数。宁可少显示,不要挤成一团。

## 6.8 导航

- 顶层入口 **≤ 7 个**(超过则需要二级分组)
- 当前态:文字变实 + 底部 2px brass 下划线(**不换底色** —— 换底色会让导航看起来像按钮组)
- 待办数用角标(rust),不用感叹号图标
- **面包屑或返回入口必须存在**,PC/移动都有 —— 低频用户容易迷路
- 移动端:汉堡全屏下拉,且**必须补上 PC 常驻但移动隐藏的信息**(当前用户、当前账期)。不能只是砍掉
- 长页(> 3 屏)必须有目录:PC 侧边 sticky,移动浮钮 + 底部 sheet;DOM 顺序内容优先,视觉位置靠 CSS `order` 调整

# 7 · 移动端:分析能力不缩水,呈现方式重构

## 7.1 前提修正:手机是常态化的分析场景

用户主力是 iOS,且 dashboard 的分析是每次都要用的核心能力 —— 不是"顺手扫一眼"。所以下面这条**不成立**,必须否掉:

> ~~移动端只负责录入与查看,复杂分析引导去 PC~~

正确的定位是:**PC 和手机做的是同一件分析,但用户的动作不同。**

| | PC 上用户在做 | 手机上用户在做 |
|---|---|---|
| 动作 | **探索** —— 横向对比、翻维度找异常、多条件交叉 | **确认与追踪** —— 这个月怎么样、上次那个问题好了吗、哪一项拖后腿 |
| 心态 | 坐下来,有时间,愿意操作 | 站着/躺着,单手,几十秒到几分钟 |
| 需要的输出 | 可自由切换的原始视图 | **结论,以及点两下能验证结论的证据** |

**铁律:任何 PC 上能得到的分析结论,手机上必须也能得到。** 允许路径不同、步骤更多,不允许"这个功能手机上没有"。

但反过来也有一条:**不许把 PC 的图直接缩小塞进窄屏。** 一张 1200px 宽的双向柱图缩到 358px,不是"移动版",是废掉的图。缩放不是适配。

## 7.2 手机分析页的四层架构

PC 的多列网格在手机上失效。手机用**纵向四层**,层级越往下越细,用户按需往下走:

| 层 | 内容 | 高度预算 | 规格 |
|---|---|---|---|
| **L1 结论层** | 1-3 句话 + 主数字 | 首屏内 | 直接说结论:"净资产 ¥3.2M,比上月 +2.1%;拖后腿的是港股(-8.4%)" |
| **L2 指标层** | 1 个英雄数字 + 横滑指标条 | ~120px | 见 §7.4 KPI 方案 |
| **L3 图表层** | 分析卡片流,每卡一个洞察 | 每卡 ≤ 320px | 卡内:标题 + 一句话结论 + 图 + [展开全屏] |
| **L4 明细层** | 可折叠的表格/列表 | 默认折叠 | 精确读数、逐条核对 |

**关键:L1 必须在首屏,且不需要用户解读图表。** 一个月来一次的用户,打开 dashboard 的第一个问题是"这个月还好吗" —— 这个问题应该由文字直接回答,不该让他自己看柱子高低去推断。

结论层的文案由工程算好(不是 LLM 现算),模板化:`{指标} {值},{方向} {幅度};{最大贡献项} {贡献}`。

## 7.3 大组件移动化的五种手段(按优先级)

遇到一个在窄屏放不下的组件,**按这个顺序试**:

| # | 手段 | 什么时候用 | 例 |
|---|---|---|---|
| **1** | **换图型** | 同一洞察有更适合窄屏的图型时。**最优解,优先考虑** | 环图(>6 类)→ 横向条形;横向瀑布 → 纵向瀑布 |
| **2** | **结论前置 + 下钻** | 图的价值主要是"得出一个结论" | 卡片给结论 + 迷你图,点开看完整图 |
| **3** | **降维** | 组件同屏展示 ≥2 个维度 | 交叉表 → 选一个主维度分组,次维度作组内行 |
| **4** | **TopN + 其他** | 类目数不可控(账户 21 个、行业 49 个) | Top 8 + "其他"聚合,点"其他"展开 |
| **5** | **全屏查看器** | 前四种都不够,图确实需要大画布 | 点卡片 → 全屏浮层(见 §7.5) |

**禁止的手段**:
- 缩小字号硬塞(违反 12px 红线)
- 图表内横向滚动(与 iOS 页面滚动冲突,详见 §7.6)
- 强制横屏(iOS 不支持 `orientation.lock`)
- "手机上不提供此分析"

## 7.4 逐个大组件的手机方案

### KPI 群(6 个)—— 英雄数字 + 横滑指标条

现状 2 列 × 3 行占满整个首屏,用户还没看到任何分析就得滚。方案:

```
┌─────────────────────────────┐
│ 净 · 资 · 产                 │  ← eyebrow
│ ¥3,241,580                  │  ← 39px,英雄数字
│ ▲ +2.1% · 较上月 +¥66,800    │  ← 变化,forest/rust
└─────────────────────────────┘
[总资产 ¥3.5M][总负债 ¥260k][紧急储备 8.2月][本月收益 +1.8%] →
 ← 横滑,scroll-snap,右缘渐隐提示
```

- 主 KPI(净资产)独占一块,`3xl` 字号 + 变化行
- 其余 5 个做横滑 chip:每个 chip 内 `eyebrow + 值`,宽度 ~44% 屏宽(露出下一个的边,暗示可滑)
- `scroll-snap-type: x mandatory` + `scroll-snap-align: start`
- 右缘渐隐 + `›` 提示(复用现有 `.lens-hscroll` 模式)

判据:**主 KPI 只能有一个。** 六个同等大小的数字 = 没有重点,用户不知道该看哪个。

### 资产配置 / 成员分布(环图)—— 类目数决定图型

| 类目数 | 手机图型 |
|---|---|
| ≤ 6 | 保留环图(直径 ≥ 160px),中心放总额,标注在扇片外侧 |
| **> 6** | **换横向条形图** —— 标签在左、条在中、金额+占比在右 |

横向条形在窄屏是**天然最优**的图型:纵向排列不受宽度限制,标签有完整空间,数值可精确标注,且每行 32px 恰好是可点高度(点击下钻)。

```
股票股权  ████████████████  ¥1.42M  43.8%
现金          ████████       ¥780k   24.1%
理财            ██████       ¥520k   16.0%
...
其他 4 项         ██         ¥210k    6.5%   ← 点击展开
```

**这条规则同时适用于 PC**:超过 7 类的环图在任何尺寸下都不该用(人眼无法比较相近扇形角度)。

### 账户双向柱(21 个账户,资产右/负债左)—— 拆成两段条形列表

双向柱在 PC 上很好(零轴居中,一眼看出资产负债结构),但 21 行 × 双向在 358px 宽内每侧只剩 ~150px,完全不可读。

方案:**拆成"资产"和"负债"两段,各自横向条形,组内降序**:

```
资 · 产                        ¥3.50M
招行储蓄卡   ██████████  ¥820,000
富途证券     ████████    ¥650,000
...
其他 6 个    ███         ¥180,000  ← 展开

负 · 债                        ¥260k
房贷         ██████████  ¥240,000
信用卡       █           ¥20,000
```

理由:手机上用户不需要"左右对比资产负债"(那是结构性认知,L1 结论层已经给了总额和比例),需要的是"哪个账户占大头"。**分段列表回答后者,双向柱回答前者** —— 前者由文字结论承担,后者不必在手机上画。

### 归因瀑布(基准 → 人赚 → 钱赚 → 基线 → 净变化)—— 改纵向瀑布

横向瀑布是最不适合窄屏的图型之一(步骤多、每步要标签+数值)。但**纵向瀑布在手机上极其自然**,长得像一张账单:

```
期初基准                    ¥3,174,780
  + 人赚(工资/结余)         +¥42,000   ████
  + 钱赚(投资收益)          +¥28,600   ███
  − 开账基线调整              −¥3,800   ▌
  ─────────────────────────────────────
  = 本期净变化               +¥66,800
    未归因                      ¥120   ← 恒等闭合检查
本期净资产                  ¥3,241,580
```

- 每行 32px,数值右对齐 tabular-nums,条长按比例
- 正负用 forest/rust(数据轴,纯文字无框)
- "未归因"是恒等闭合的自检项,必须显示,值 > 阈值时变 rust

这是"换图型"手段的最佳范例:**同样的信息、同样的严谨性,换个方向就从"不可用"变成"比 PC 版更易读"**。建议 PC 端也考虑采用。

### 近 12 期堆叠柱(钱赚按维度 TopN)—— 期数降到 6 + 图例转列表

- 默认显示**最近 6 期**(不是 12),配 `6 / 12 / 24` 期数切换 chip
- 每期柱宽 ≥ 24px,间距 ≥ 8px → 6 期在 358px 内舒适
- 图例不放图上(挤),转成图下方的列表:`色块 + 名称 + 本期值 + 迷你 sparkline`
- 类目 Top 5 + "其他",与 PC 一致

### 趋势折线(净资产 / 收支 / 余额)—— 默认 6 期,不横滑

- 默认最近 6 期,可切 12 / 24
- **数据点间距 ≥ 32px** 才能点中;若切到 24 期导致间距不足,自动隐藏数据点标记只留线,并关闭点击查询(改用底部数据表)
- 双系列(名义 vs 购买力 / 收入 vs 支出)在手机上保留 —— 两条线不挤,这是可以不降级的
- **不做图表内横向滚动**(§7.6 iOS 冲突)

### 交叉表(lens pivot)—— 降维成分组卡片,横滑表作为备选路径

交叉表是最难的一个。手机上给**两条路径**:

**路径 A(默认)· 降维成分组列表** —— 主维度作组标题,次维度作组内行:

```
▼ 迪娃                            ¥1,842,000  56.8%
    股票股权        ¥820,000   44.5%  ████████
    现金            ¥520,000   28.2%  █████
    理财            ¥502,000   27.3%  █████
▼ 王二狗                          ¥1,120,000  34.6%
    ...
▶ 共同                              ¥279,580   8.6%
```

- 组可折叠,默认展开第一组
- 组内行按值降序,带占比条
- 提供"**转置**"按钮(主/次维度对调)—— 这是降维方案保留完整分析能力的关键:想按资产类型看,点一下转置即可
- 指标多选时,组内每行显示主指标,次指标以小字附在右侧(≤2 个),超过 2 个走路径 B

**路径 B · 全屏横滑表** —— 保留真正的二维表:
- 进入全屏查看器,首列 sticky + 右缘阴影
- 允许**容器级**横滑(不是图表内滚动),`overscroll-behavior-x: contain` 防止触发 Safari 返回手势
- 提示"横屏更清晰"(提示,不锁定)

判据:**默认给路径 A(能读)**,路径 B 作为"我要看原始交叉"的显式入口。不要默认丢一张横滑表给用户。

### 旭日图(多层下钻)—— 环 + 当前层列表并存

环图在手机上小,但它的价值是**结构感**(层级关系),而精确读数应该交给列表。方案:上下分区:

```
[面包屑] 全部 › 股票股权 › 电子        ← 下钻路径,可点回退
┌──────────────────┐
│   ◕ 旭日环        │  ← 直径 = min(屏宽-32, 280)
│   中心:当前层总额 │     点击扇片 = 下钻
└──────────────────┘
当前层 · 电子(3 项)
  半导体      ¥260,000  52.0%  ████████
  消费电子    ¥150,000  30.0%  ████
  元件        ¥ 90,000  18.0%  ██
```

- **环负责结构,列表负责读数** —— 两者数据同源,选中态同步高亮
- 下钻:点扇片 或 点列表行,都下钻
- **必须有面包屑 + 显式返回**(iOS PWA 没有系统返回手势,见 §7.6)
- 环内不标文字(太小),标注全部交给下方列表

### 长表格(账户列表 / 流水)—— 卡片流,见 §6.4

不做横滑表格。列表转卡片,每卡一个主体,金额最大最强。

### 风险分布 / 财富水位 / 储蓄率 —— 结论前置 + 迷你图

这几个的分析价值集中在"一个结论 + 一个位置感",适合手段 2:

```
┌─────────────────────────────┐
│ 财 · 富 · 水 · 位            │
│ 你在「稳健积累」区间          │  ← 结论,lg 字号
│ ▓▓▓▓▓▓▓░░░░  62%           │  ← 迷你水位条
│ 距下一档还需 ¥480,000        │
│                    [看详情 →]│
└─────────────────────────────┘
```

结论 + 位置 + 差距 —— 手机上这就够了,完整的分档图放全屏查看器。

## 7.5 统一「图表全屏查看器」(一次投入,覆盖全部 13+ 图表)

不要为每个图各写一套移动适配。做**一个通用全屏查看器**,所有分析卡片的 [展开] 都进这里:

```
┌─────────────────────────────┐
│ 资产配置 · 2026-07      [图|表]│  ← 标题 + 图/表切换
├─────────────────────────────┤
│                             │
│      (大画布,占满可用高度)   │
│                             │
├─────────────────────────────┤
│ 图例 / 当前层列表(可滚)      │
├─────────────────────────────┤
│  [维度切换 chip 横滑]         │
│         ⌄ 下滑关闭 / [关闭]   │  ← 底部,拇指可达
└─────────────────────────────┘
```

规格:

| 要素 | 规格 | 为什么 |
|---|---|---|
| 触发 | 卡片右下 `[展开 →]`,或点图本体 | — |
| 进出动效 | 从卡片位置放大 260ms,`cubic-bezier(.22,1,.36,1)` | 保持空间连续性,用户知道自己在哪 |
| 关闭 | **底部关闭按钮 + 下滑手势**,不用左上 × | iPhone 单手握持时左上角是最难到的位置 |
| 高度 | `100dvh`(不用 `100vh`)+ `padding-bottom: env(safe-area-inset-bottom)` | iOS Safari 地址栏收放会改变 `vh` |
| **图/表切换** | 必备。表格视图给精确数值 + 可复制 | 手机上想读准数时,表比图强;同时解决读屏无障碍 |
| 维度切换 | 底部 chip 横滑(不放顶部) | 底部是拇指区,顶部是"看"的区 |
| 横屏 | 不锁定;检测到 `orientation` 变化时重新计算画布 | iOS 不支持锁定 |
| 缩放 | 交叉表等宽内容允许原生双指缩放;其他图禁用(重绘代替) | — |

**"图/表切换"是这个查看器最重要的功能**,别当成附属项:手机屏幕上读精确金额,表格永远优于图表;而图表擅长的是趋势和比例。给用户切换权,比我们替他决定更好。

## 7.6 iOS / PWA 专项约束(硬性,逐条必守)

主力用户是 iOS,以下每条都有具体的失效场景,不是理论风险:

| # | 约束 | 后果 | 做法 |
|---|---|---|---|
| 1 | **`100vh` 不可靠** | Safari 地址栏收放时 `vh` 变化,全屏浮层被裁或超出 | 用 `100dvh`,降级 `-webkit-fill-available` |
| 2 | **PWA standalone 无系统返回手势** | 下钻后用户出不来,只能杀掉重开 | 所有下钻/全屏**必须有应用内显式返回**,且带面包屑 |
| 3 | **底部安全区** | home indicator 压住底部按钮 | 固定底部元素一律 `padding-bottom: max(16px, env(safe-area-inset-bottom))` |
| 4 | **输入框 < 16px 触发整页缩放** | 填报时页面突然放大,布局错乱 | 移动端输入框 `font-size ≥ 16px`,无例外 |
| 5 | **`screen.orientation.lock` 不支持** | 强制横屏方案在 iOS 直接失效 | 只提示"横屏更清晰",不锁定 |
| 6 | **边缘横滑 = Safari 返回手势** | 图表/表格横滑时误触发返回,离开页面 | 横滑容器 `overscroll-behavior-x: contain`;**横滑区不贴屏幕左右边缘**(留 ≥16px 边距) |
| 7 | **长按触发系统菜单/链接预览** | 长按图表出现"拷贝图片";隐私态长按金额出链接预览 | 图表容器 `-webkit-touch-callout: none`;`<a>` 内的敏感数字同样处理 |
| 8 | **无 hover** | 依赖 hover 的 tooltip 在手机上永久不可见 | 数值直接标在图上(§6.7 铁律);tooltip 改点击触发,点击空白关闭 |
| 9 | **momentum scroll 与内部滚动冲突** | 内部区域滚到底后继续拖会带动整页 | 内部滚动容器 `overscroll-behavior: contain` |
| 10 | **拇通可达区** | 顶部操作在 6.1" 屏单手够不到 | **高频操作放屏幕下半部**;顶部只放"看"的内容和低频操作 |
| 11 | **PWA 无地址栏 = 无 URL 感知** | 用户不知道自己在哪一层 | 每页必须有标题栏 + 返回;深层页面给面包屑 |
| 12 | **状态栏与页面接缝** | `theme-color` 深色 + 页面米色 = 明显色带 | `theme-color` 与 `--paper` 一致 |

## 7.7 图表触摸交互规格

| 交互 | 规格 |
|---|---|
| 读数 | **优先靠直接标注**;需要精确值走"表"视图 |
| 点选 | 点击扇片/柱/点 → 高亮 + 底部信息条(不用浮动 tooltip,浮层会被手指遮住) |
| 下钻 | 点击 = 下钻(不用双击、不用长按);必须配面包屑 + 返回 |
| 取消选中 | 点击图表空白区 |
| 命中区域 | 每个可点图元 ≥ 32×32px 的等效命中区;条形图行高 ≥ 32px |
| 切维度 | 底部 chip 横滑,`scroll-snap` |

**图表最小可读尺寸(低于此值必须换图型,不许缩小)**:

| 图型 | 最小尺寸 |
|---|---|
| 环图 / 饼图 | 直径 ≥ 160px,且类目 ≤ 6 |
| 旭日图 | 直径 ≥ 220px,层数 ≤ 3 |
| 横向条形 | 每行高 ≥ 24px(可点则 ≥ 32px) |
| 柱状图 | 柱宽 ≥ 20px,间距 ≥ 8px |
| 折线图 | 数据点间距 ≥ 32px(可点)/ ≥ 12px(仅看线) |
| 交叉表 | 单元格 ≥ 56×32px,首列 ≥ 88px |

这张表是**换图型的触发条件**:算一下容器宽度能不能满足,不满足就按 §7.3 换,而不是把字号调小。

## X · 并列同类图表 / 并列同类元素:必须共用同一套尺度

**这一节是用户在 2026-07-28 明确要求补进规范的**,原话:
「都是饼图 那就保持大小样式一样,现在奇奇怪怪的,两个饼图差距很大,**这种常识问题**,
落到记忆和规范里面,不要我每次提出来,你自己要先自查」。

### 规则

**同一页面上语义同级、并列展示的元素,必须共用同一套尺度。**
适用范围不限于图表:并列的 KPI 卡、并列的按钮组、并列的空态插图,同理。

对图表,"同一套尺度"具体指:

| 维度 | 要求 |
|---|---|
| 图型 | 相同(不许一个环一个条) |
| 容器高度 | 相同 —— **共用同一个 class**,不许各写 `h-[348px]` / `h-[262px]` |
| 主体尺寸 | 相同 —— 环图**把半径写死**,不要让它由「容器高 − 标题 − 图例」推导 |
| 图例位置 / 字号 / 内距 / 标题字号 | 相同 |

### 为什么"容器高度相同"还不够

环图直径默认由剩余空间推出来。两个图的图例行数往往不同
(资产配置 5 项 3 行 / 按成员 3 项 1 行)→ 即使容器一样高,**直径依然不同**。
所以必须把半径写死,并把整组尺度参数收进一个共享常量(本项目是 `PAIR`),
两个图传同一组值。

### 反面案例(本项目真实踩过)

1. **v1.6.4**:按类目数决定图型(`>6 类走条形`)→ 资产配置 7 类走条形、按成员 3 类走环图
   → 同一屏一个条一个环。**按数据量分叉图型,必然产出"同类并列不一致"。**
2. **v1.6.11**:两个都改成环图了,但容器高度各写各的(348 / 262)+ 半径由剩余空间推导
   → 两个环一大一小。

### 操作行 / 按钮组(2026-10-13 维护者:「危险操作的按钮太丑陋了,甚至也没对齐 —— 不要老是犯这类错误」)

v1.33 的账户编辑页「危险操作」:两行都是「按钮 + 一句说明」用 flex 排,按钮「归档此账户」宽 103、「删除账户」宽 90
→ 两句说明的起点差了 13px;两个按钮一黑框一红框、字号 11px,像临时摆上去的。**按钮宽度决定了后面的文字从哪开始,这本身就是错的布局。**

| 规则 | 怎么做 |
|---|---|
| 「说明 + 按钮」的多行操作区 | 每行 **grid 两列**:左「名称(粗)+ 说明」,右按钮;说明永远从同一列起,按钮右缘对齐 —— 共用件 `.danger-zone`(style.css) |
| 同组按钮 | **同宽同高**(固定 `width` 或统一 `min-width`),文案短而同构(「归档」「删除」,不是「归档此账户」「删除账户」) |
| 主次 | 最危险的一个用实心(红底白字),其余描边;不混用黑框和红框 |
| 手机 | 按钮整行放在说明下面(≥ 42px 高) |
| 机器校验 | e2e 里对并列按钮 `ui.sameSize(...)`,对说明列量 `getBoundingClientRect().left` 是否一致 —— 能量的就别靠眼睛(flow 49 第 6 段) |

## Y · `⋯` 收纳只放低频维护动作,能力入口不得进折叠

**规则**

| 是什么 | 放哪 |
|---|---|
| **能力入口** —— 通往一整套有自己页面或流程的功能(券商同步、持仓管理、AI 截图填报、提前还贷决策器、资产打标) | **行内一眼可见**,带文字标签(不能只有图标) |
| **低频维护动作** —— 归档、恢复、删除、导出 CSV | 可以收进 `⋯` / `details` |

**为什么要单独写一条**:v1.6「UED 批次5 · affordance 与收纳」按「行内按钮太多」的**视觉密度**
把账户页 PC 行内的「券商」按钮和「归档 / 导出 / 划转」一起收进了 `⋯`。用户随后报障
「券商自动对接的入口是不是丢了」—— 功能一行没删,但**对用户来说"还在但找不到"和"没了"没区别**。

**错在哪**:按**数量**收纳,而不是按**类别**。同一行里的控件不是等价的 ——
能力入口是这一行**通往别处的门**,维护动作是**对这一行本身的操作**。收纳只该动后者。

**配套判据**:能力入口一律登记进 `scripts/entry-points.json`,守护 `v1623-ENTRY-VIS` 在
PC 1440×900 + 移动 390×844 两端渲染真页面断言「有面积 + `elementFromPoint` 命中自己 + 不在折叠容器内」。
策略与实现细节见 `docs/entry-points.md`。

**顺带一条**:能力入口用**有框**样式(`btn-paper` / `btn-ghost`),不要用下划线文字链 ——
按 §6.1「有框=要你做决定」,文字链渲染出来像副标题说明,读不出"这是个能去的地方"
(v1.6.23 补提前还贷入口时第一版就做成了文字链,截图一看像图表副标题,自查改掉)。
